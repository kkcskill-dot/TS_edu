1. 이력 데이터 수집 아키텍처 (Memory SGA to Disk Storage)

데이터베이스의 실시간 세션 활동 상태는 SGA 메모리 버퍼에 1초 단위로 쌓이고, 거시적 누적 통계 지표는 디스크에 1시간마다 영구 보존됩니다.

ASH (Active Session History) : 메모리 순환 버퍼
  • 수집 간격: 1초 (1 Second) 극초고속 샘플링
  • 수집 대상: CPU 점유 중이거나 특정 자원 획득 대기 상태인 ACTIVE 세션
  • 최적화: 대기 상태가 아닌 휴식 세션은 기록에서 완전 배제하여 부하 1% 미만 유지
  • 보관 위치: SGA 내부의 고속 순환 메모리 버퍼 (Circular Buffer, 약 1~2시간 분량 보존)
AWR (Automatic Workload Repository) : 디스크 영구소
  • 수집 간격: 기본 1시간 (1 Hour) 간격 스냅샷 저장
  • 수집 대상: 전체 DB 리소스 누적 지표 (CPU 사용량, 물리 I/O, SQL 통계)
  • 백그라운드 프로세스 동작 체계:
    - MMON: 1시간 주기 디스크 스냅샷 기입 총괄
    - MMNL: ASH 버퍼가 60% 차거나 10초 경과시 10% 비율로 압축 샘플하여 디스크로 Flush
  • 보관 위치: SYSAUX 테이블스페이스 디스크 (기본 8일간 영구 보존)
DBA의 정석 분석 흐름: 거대한 시스템 전체 부하 추이는 AWR 리포트를 통해 거시적으로 먼저 스캐닝한 후, 이슈가 포착된 특정 시간대의 초단위 세션 블로킹 병목 관계는 ASH 데이터를 조회하여 미시적으로 정확히 짚어냅니다.

3. 데이터베이스 4대 주요 Foreground 대기 이벤트 백과사전

데이터베이스 대기 병목을 초래하는 상위 이벤트들의 아키텍처 상 메커니즘과 DBA의 튜닝 조치를 심층적으로 학습합니다.

db file sequential read (단일 블록 물리 읽기 대기)
  • 발생 원인: B-Tree 인덱스 스캔 후 테이블 블록을 한 개씩 순차적으로 디스크에서 조회할 때 대기 발생.
  • 성능 진단: 가져올 범위가 광범위한데 억지로 인덱스 탐색을 고수하여 대량의 무작위 디스크 접근(Random I/O)이 누적되는 상태.
  • DBA 조치: 쿼리 선택도(Selectivity)를 엄격히 분석하여 범위가 넓은 배치 작업 등은 차라리 다중 블록 읽기(Full Table Scan)가 적용되도록 옵티마이저 힌트 기입. 결합 인덱스(Composite Index) 재구성으로 테이블 조인 접근 회수 최소화.
db file scattered read (다중 블록 물리 읽기 대기)
  • 발생 원인: 인덱스 부재 등으로 인해 테이블 전체를 읽어 들이는 Full Table Scan 발생 시 디스크에서 연속된 다중 블록을 퍼올리는 대기.
  • 성능 진단: 조건절 우변 컬럼 변형, Leading Wildcard 기법(LIKE '%abc') 사용 등으로 정상적인 B-Tree 인덱스가 작동되지 않고 옵티마이저가 풀 스캔을 강행하는 상태.
  • DBA 조치: 조건절 컬럼에 대한 최적화된 B-Tree 인덱스를 구축하고, 묵시적 형변환이나 좌변 컬럼 변형을 걷어내어 정상 인덱스 탐색으로 옵티마이저 유도.
enq: TX - row lock contention (행 레벨 배타적 DML 락 대기)
  • 발생 원인: 특정 레코드의 갱신(UPDATE)/삭제(DELETE) 처리를 위해 독점 락을 얻은 선행 트랜잭션이 종결되기 전에 후행 세션이 동일 레코드를 수정하려 할 때 락 반환 전까지 대기 큐에서 대기.
  • 성능 진단: 선행 프로세스의 상태가 INACTIVE인 채 락을 잡고 있다면 전형적인 예외 처리 설계 결함으로 인한 Connection Leak 발생 상태.
  • DBA 조치: 응용 프로그램 소스 코드의 try-catch-finally 구문을 분석하여 오류 발생 시 반드시 connection.rollback()이 가동되어 락을 안전히 반납하도록 보강. WAS의 커넥션 타이머 회수 튜닝 적용.
latch: shared pool / library cache (메모리 구조체 래치 경합 대기)
  • 발생 원인: Shared Pool 메모리 내에 새로운 SQL 문장을 파싱하여 등록하는 하드 파싱(Hard Parsing) 중 메모리 캐시 헤더를 잠그는 래치를 얻기 위해 대기.
  • 성능 진단: 초당 하드 파싱 건수 폭증으로 인해 CPU 사용량이 I/O 없이 100% 임계 한계 상태를 유지.
  • DBA 조치: SQL 조건절의 동적 가변 상수를 모두 제거하고 PreparedStatement 계열의 표준 바인드 파라미터 방식으로 치환하여 분석 계획 재사용 유도.
4. 실전 이슈 사례 분석 및 해결 코드 (Case Studies)

실무에서 맞닥뜨리는 치명적인 DB 지연 이슈의 실제 AS-IS 오류 코드와 교정된 TO-BE 코드를 정밀 분석합니다.

[이슈 1] 예외 처리 설계 결함으로 인한 락 경합 이슈 (Connection Leak)

- AS-IS (오류): 트랜잭션 수동 제어(setAutoCommit(false)) 중 비즈니스 런타임 오류가 발생 시, catch 블록에서 rollback() 처리가 아예 누락되었습니다. 이로 인해 UPDATE 쿼리가 가졌던 배타적 레코드 락이 WAS 풀로 반환되어도 그대로 유지되어 후속 세션들이 enq: TX - row lock contention으로 줄줄이 뻗어버리게 됩니다.
- TO-BE (개선): catch (Exception e) 안에서 conn.rollback()을 완벽하게 명시하고, finally 블록에서 안전하게 커넥션 리소스를 클로즈시켜 락 누설을 100% 예방합니다.

[이슈 2] 상수 대입형 쿼리 남발에 따른 CPU 고갈 이슈 (Hard Parse)

- AS-IS (오류): MyBatis 매퍼 등에서 member_no = ${memberNo}와 같이 리터럴 결합 문법($)을 남발하여 실행 시 쿼리 문자열이 매 요청마다 물리적으로 계속 달라집니다. 이에 컴파일러가 매번 새 쿼리로 분석하여 하드 파싱을 무한 가동하느라 CPU 리소스가 고갈되었습니다.
- TO-BE (개선): 표준 바인드 파라미터 문법인 member_no = #{memberNo} (# 문법)으로 고칩니다. 분석된 쿼리가 Shared Pool 라이브러리 캐시에 가볍게 고정되어 재활용되므로 CPU 부하가 즉각 0%에 가깝게 수렴합니다.

  • 보관 위치: SGA 내부의 고속 순환 메모리 버퍼 (Circular Buffer, 약 1~2시간 분량 보존)
AWR (Automatic Workload Repository) : 디스크 영구소
  • 수집 간격: 기본 1시간 (1 Hour) 간격 스냅샷 저장
  • 수집 대상: 전체 DB 리소스 누적 지표 (CPU 사용량, 물리 I/O, SQL 통계)
  • 백그라운드 프로세스 동작 체계:
    - MMON: 1시간 주기 디스크 스냅샷 기입 총괄
    - MMNL: ASH 버퍼가 60% 차거나 10초 경과시 10% 비율로 압축 샘플하여 디스크로 Flush
  • 보관 위치: SYSAUX 테이블스페이스 디스크 (기본 8일간 영구 보존)
DBA의 정석 분석 흐름: 거대한 시스템 전체 부하 추이는 AWR 리포트를 통해 거시적으로 먼저 스캐닝한 후, 이슈가 포착된 특정 시간대의 초단위 세션 블로킹 병목 관계는 ASH 데이터를 조회하여 미시적으로 정확히 짚어냅니다.
2. AWR 성능 공식 및 임계값 수학적 진단

데이터베이스 인스턴스 전반의 시스템 가동 강도 및 자원 효율성을 정량적인 공식을 통해 수학적으로 분석합니다.

DB Time (데이터베이스 가동 누적 시간) DB Time = CPU Time + Wait Time (Non-Idle)

활성 상태인 프로세스들이 실제로 CPU 상에서 연산하거나 자원 대기를 겪은 모든 시간을 기계적으로 더한 누적 절대시간입니다. 이 수치가 물리적인 측정 주기 대비 비대해지면 성능 장애가 임박했음을 나타냅니다.

AAS (Average Active Sessions : 평균 활성 세션 수) AAS = DB Time / 측정 지속 시간 (초)

해당 구간 동안 동시에 구동/대기 중이었던 평균 세션 수입니다.
[임계값 판단 기법]:
- AAS <= 물리 CPU Core 수: 시스템 리소스에 여유가 있는 매우 건전하고 쾌적한 상태.
- AAS ~= 물리 CPU Core 수: 하드웨어의 모든 성능 한계 용량을 사용 중인 과밀 상태.
- AAS > 물리 CPU Core 수: CPU 런 큐(Run Queue)에 대기가 급증하여 지수적인 응답 지연이 빚어지는 경고 병목 상태.

Soft Parse Ratio (실행 계획 소프트 파싱 성공률) Soft Parse % = (1 - (Hard Parses / Total Parses)) * 100

이 수치는 99.9% 이상 유지되어야 마땅합니다. 99% 이하로 곤두질치는 경우, 바인드 파라미터 누락으로 인해 컴파일러가 대량의 SQL 실행 계획을 실시간으로 컴파일하여 Shared Pool 메모리를 점유하고 있음을 증명합니다.

3. 데이터베이스 4대 주요 Foreground 대기 이벤트 백과사전

데이터베이스 대기 병목을 초래하는 상위 이벤트들의 아키텍처 상 메커니즘과 DBA의 튜닝 조치를 심층적으로 학습합니다.

db file sequential read (단일 블록 물리 읽기 대기)
  • 발생 원인: B-Tree 인덱스 스캔 후 테이블 블록을 한 개씩 순차적으로 디스크에서 조회할 때 대기 발생.
  • 성능 진단: 가져올 범위가 광범위한데 억지로 인덱스 탐색을 고수하여 대량의 무작위 디스크 접근(Random I/O)이 누적되는 상태.
  • DBA 조치: 쿼리 선택도(Selectivity)를 엄격히 분석하여 범위가 넓은 배치 작업 등은 차라리 다중 블록 읽기(Full Table Scan)가 적용되도록 옵티마이저 힌트 기입. 결합 인덱스(Composite Index) 재구성으로 테이블 조인 접근 회수 최소화.
db file scattered read (다중 블록 물리 읽기 대기)
  • 발생 원인: 인덱스 부재 등으로 인해 테이블 전체를 읽어 들이는 Full Table Scan 발생 시 디스크에서 연속된 다중 블록을 퍼올리는 대기.
  • 성능 진단: 조건절 우변 컬럼 변형, Leading Wildcard 기법(LIKE '%abc') 사용 등으로 정상적인 B-Tree 인덱스가 작동되지 않고 옵티마이저가 풀 스캔을 강행하는 상태.
  • DBA 조치: 조건절 컬럼에 대한 최적화된 B-Tree 인덱스를 구축하고, 묵시적 형변환이나 좌변 컬럼 변형을 걷어내어 정상 인덱스 탐색으로 옵티마이저 유도.
enq: TX - row lock contention (행 레벨 배타적 DML 락 대기)
  • 발생 원인: 특정 레코드의 갱신(UPDATE)/삭제(DELETE) 처리를 위해 독점 락을 얻은 선행 트랜잭션이 종결되기 전에 후행 세션이 동일 레코드를 수정하려 할 때 락 반환 전까지 대기 큐에서 대기.
  • 성능 진단: 선행 프로세스의 상태가 INACTIVE인 채 락을 잡고 있다면 전형적인 예외 처리 설계 결함으로 인한 Connection Leak 발생 상태.
  • DBA 조치: 응용 프로그램 소스 코드의 try-catch-finally 구문을 분석하여 오류 발생 시 반드시 connection.rollback()이 가동되어 락을 안전히 반납하도록 보강. WAS의 커넥션 타이머 회수 튜닝 적용.
latch: shared pool / library cache (메모리 구조체 래치 경합 대기)
  • 발생 원인: Shared Pool 메모리 내에 새로운 SQL 문장을 파싱하여 등록하는 하드 파싱(Hard Parsing) 중 메모리 캐시 헤더를 잠그는 래치를 얻기 위해 대기.
  • 성능 진단: 초당 하드 파싱 건수 폭증으로 인해 CPU 사용량이 I/O 없이 100% 임계 한계 상태를 유지.
  • DBA 조치: SQL 조건절의 동적 가변 상수를 모두 제거하고 PreparedStatement 계열의 표준 바인드 파라미터 방식으로 치환하여 분석 계획 재사용 유도.
4. 실전 이슈 사례 분석 및 해결 코드 (Case Studies)

실무에서 맞닥뜨리는 치명적인 DB 지연 이슈의 실제 AS-IS 오류 코드와 교정된 TO-BE 코드를 정밀 분석합니다.

[이슈 1] 예외 처리 설계 결함으로 인한 락 경합 이슈 (Connection Leak)

- AS-IS (오류): 트랜잭션 수동 제어(setAutoCommit(false)) 중 비즈니스 런타임 오류가 발생 시, catch 블록에서 rollback() 처리가 아예 누락되었습니다. 이로 인해 UPDATE 쿼리가 가졌던 배타적 레코드 락이 WAS 풀로 반환되어도 그대로 유지되어 후속 세션들이 enq: TX - row lock contention으로 줄줄이 뻗어버리게 됩니다.
- TO-BE (개선): catch (Exception e) 안에서 conn.rollback()을 완벽하게 명시하고, finally 블록에서 안전하게 커넥션 리소스를 클로즈시켜 락 누설을 100% 예방합니다.

[이슈 2] 상수 대입형 쿼리 남발에 따른 CPU 고갈 이슈 (Hard Parse)

- AS-IS (오류): MyBatis 매퍼 등에서 member_no = ${memberNo}와 같이 리터럴 결합 문법($)을 남발하여 실행 시 쿼리 문자열이 매 요청마다 물리적으로 계속 달라집니다. 이에 컴파일러가 매번 새 쿼리로 분석하여 하드 파싱을 무한 가동하느라 CPU 리소스가 고갈되었습니다.
- TO-BE (개선): 표준 바인드 파라미터 문법인 member_no = #{memberNo} (# 문법)으로 고칩니다. 분석된 쿼리가 Shared Pool 라이브러리 캐시에 가볍게 고정되어 재활용되므로 CPU 부하가 즉각 0%에 가깝게 수렴합니다.

10대 지표는 부하·활동(①~④) / 메모리(⑤~⑥) / I·O·효율(⑦~⑨) / 원인 SQL(⑩) 네 그룹으로 묶어 봅니다. 그룹은 병목이 전파되는 계층입니다. 자세한 추출 SQL과 판독 기준은 학습자료 → 4강을 참고하세요.

두 가지 대원칙

① 항상 기준선(B0)과 비교하라. 절대 수치 하나로는 정상 여부를 알 수 없습니다. Hard Parse 100/s는 기준선이 1.2/s일 때 비로소 위험입니다.

② 결과 지표와 원인 지표를 구분하라. AAS = DB CPU AAS + Wait AAS. AAS가 코어를 넘은 것은 "바쁘다"는 결과일 뿐, "CPU 부족"이라는 원인이 아닙니다. 원인은 그 아래 Hard Parse·카디널리티 오차·잦은 commit에 있습니다.

대표 함정
  • Buffer Hit% 하락 ≠ 메모리 부족. 비효율 SQL이 논리읽기(분모)를 키운 결과일 때가 많습니다.
  • 리터럴 SQL은 FMS로 묶어라. 개별 SQL_ID로는 파싱 부하가 숨습니다.
  • log file sync ≠ log file parallel write. sync만 크면 스토리지가 아니라 잦은 commit이 원인입니다.
  • 결과 지표(AAS·Host CPU·Hit%)를 근거로 단독 제출하면 감점.
