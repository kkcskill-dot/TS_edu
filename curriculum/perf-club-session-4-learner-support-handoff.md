# 성능진단 소모임 4회차 — 수강생 오개념·운영 지원 핸드오프

> **후속 콘텐츠 설계자 전달안 v1.0 · 2026-07-23**  
> 연계 기준: `perf-club-session-4-one-page-plan.md`, `perf-club-session-4-integrated-diagnostic-scenario.md`  
> 대상: Oracle 운영·기술지원 1~5년 / 2~3인 1조 / 240분

## 1. 운영 관점 핵심 판단

4회차의 가장 큰 난점은 지표의 뜻을 외우는 것이 아니라 **동시에 변하는 10개 지표에서 원인·증폭 요인·결과를 시간 순서로 분리하는 것**이다. 1~3회차 자료에서 학습한 단일 임계값 중심 표현 때문에, 수강생은 높은 수치 하나를 발견하면 바로 원인과 조치를 확정할 가능성이 높다.

따라서 후속 콘텐츠는 모든 화면과 해설에서 다음 문장 구조를 반복해야 한다.

> **관찰 사실(수치·시각) → 비교 기준 → 원인 가설 → 추가 확인 증거 → 조치·위험·검증 조건**

정답은 “AAS가 높다”, “Hit Ratio가 낮다”가 아니라, **09:30 Hard Parse 선행 상승 → SQL군 귀속 → 카디널리티 오차·TEMP spill → 잦은 commit이 더해진 복합 병목**을 최소 3개의 독립 증거로 설명하는 것이다.

## 2. 10개 지표별 예상 오개념·난점과 필수 Q&A

| 지표 | 예상 오개념·학습 난점 | 수강생에게 되물을 Q&A 포인트 | 정답 판별에 필요한 증거 | 콘텐츠 설계 장치 |
|---|---|---|---|---|
| **1. AAS** | “AAS 19 > 8코어이므로 CPU 병목”으로 즉시 확정한다. AAS가 CPU와 비유휴 대기를 함께 포함한다는 점, 구간 길이에 따른 평균 희석을 놓친다. | **Q. AAS 19 중 실제 CPU 사용분은 얼마인가?** A. DB CPU 6.7 AAS이며 나머지는 대기다. **Q. AAS만으로 CPU 포화를 확정할 수 있는가?** A. 아니다. Host CPU·run queue·ON CPU/WAITING 분해가 필요하다. | 같은 1분 구간의 AAS, DB CPU AAS, Wait AAS, Host CPU | AAS 막대를 ON CPU/WAITING 누적 막대로 제공하고, ‘8코어 선’을 원인 판정선이 아닌 참고선으로 표기 |
| **2. DB CPU / Host CPU** | DB CPU와 Host CPU(%)를 같은 단위로 직접 비교한다. Host 92%를 전부 Oracle 사용량으로 보거나 DB CPU 6.7 AAS를 67%로 오독한다. | **Q. Host CPU 92%는 Oracle만의 사용량인가?** A. 아니다. 타 프로세스와 run queue를 확인한다. **Q. 파싱과 SQL 실행 중 무엇이 CPU 상승에 기여했는가?** A. T1~T2 선후관계와 Top SQL CPU·parse time CPU로 분해한다. | 코어 수, DB CPU AAS, Host user/system/iowait, run queue, parse time CPU, SQL CPU | 단위 배지(`AAS`, `%`, `초`)를 고정 노출하고 서로 다른 단위의 직접 뺄셈을 금지하는 미니 문항 배치 |
| **3. 비유휴 대기 AAS / Top Wait** | Top Wait 1위를 곧 근본 원인으로 본다. `CPU time`을 대기 이벤트로 취급하거나 wait count가 많으면 가장 심각하다고 판단한다. | **Q. 대기는 원인인가 결과인가?** A. 둘 다 가능하므로 시작 시각과 SQL 귀속을 확인한다. **Q. 무엇을 함께 봐야 하는가?** A. Wait AAS·총시간·평균/분위 latency·횟수·SQL_ID·session state다. | AWR Top Timed Events, ASH event/session_state/sql_id/module의 1분 집계 | 이벤트명만 주지 말고 AAS·총시간·평균 대기·샘플 비중을 함께 제공. 원인/결과 카드 분류 활동 포함 |
| **4. Physical Reads/s** | 물리 읽기 증가를 곧 스토리지 장애 또는 Buffer Cache 부족으로 본다. 총량만 보고 실행 횟수 증가와 실행당 비효율을 구분하지 않는다. | **Q. 읽기 증가는 실행 수 증가 때문인가, 한 번 실행할 때 더 읽어서인가?** A. `delta reads / delta executions`로 분해한다. **Q. 먼저 오른 것은 reads/s인가 latency인가?** A. reads/s 선행이면 SQL 유발 수요 폭증 가능성이 높다. | SQL별 physical reads, executions, reads/execution, I/O latency 타임라인 | 총 Reads와 Reads/Execution을 나란히 제시하고 둘 중 하나만으로 답하면 힌트 제공 |
| **5. I/O latency** | DB의 17ms/31ms를 보자마자 디스크 불량으로 확정한다. single-block과 TEMP I/O, DB wait와 스토리지 장비 latency의 정의 차이를 섞는다. | **Q. 지연 상승 전에 요청량이 증가했는가?** A. 타임라인으로 확인한다. **Q. 어떤 I/O를 비교하는가?** A. 블록 크기·읽기 유형·동시 요청 수가 같은 조건이어야 한다. | reads/s·TEMP throughput·DB wait latency·OS/storage latency·queue depth | “저장장치 장애”와 “DB 수요 폭증” 두 가설을 동시에 적고 각 가설의 반증 자료를 요구 |
| **6. 메모리 압력(PGA/TEMP)** | 총 PGA가 target 이하면 메모리 문제는 없다고 생각하거나, TEMP spill을 발견하자마자 PGA 증설을 정답으로 고른다. Buffer Cache와 PGA를 혼동하기도 한다. | **Q. 인스턴스 총 PGA가 여유여도 개별 SQL이 spill할 수 있는가?** A. 가능하다. **Q. 증설 전에 무엇을 입증할까?** A. one-pass/multipass, plan MEMSTATS, TEMP wait, 대상 SQL과 데이터량이다. | workarea one-pass/multipass, TEMP GB/h, `OMem/1Mem/Used-Mem`, ASH TEMP wait | SGA/PGA/TEMP 경로 그림과 “SQL 축소→동시도 조정→PGA 검토” 순서 선택 문항 제공 |
| **7. Buffer Cache 지표** | “Hit% 95% 미만 = Buffer Cache 증설”이라는 고정 규칙을 적용한다. 반대로 99%면 성능이 좋다고 단정한다. 비율의 분모 효과를 어려워한다. | **Q. Hit% 91.5%만으로 메모리 부족을 확정할 수 있는가?** A. 아니다. logical/physical reads와 업무 특성을 함께 본다. **Q. 99%인데도 느릴 수 있는가?** A. 막대한 logical I/O로 CPU 병목이 가능하다. | Buffer Hit%, logical reads/s, physical reads/s, SQL별 buffers/execution, 작업 유형 | 동일 Hit%이지만 절대량이 다른 2개 사례를 비교시키고 “비율+절대량+실행당” 3칸을 모두 채우게 함 |
| **8. 파싱 지표** | Soft Parse% 하락만으로 바인드 미사용을 확정하거나 Hard Parse 100/s를 모든 시스템의 절대 장애선으로 사용한다. SQL_ID 하나만 찾아 리터럴 SQL군을 놓친다. | **Q. 165 Hard Parses/s가 문제라는 근거는 절대값뿐인가?** A. 기준선 1.2/s 대비 상승, CPU·library cache 경합 동반, T1 선행이 근거다. **Q. 파편화 SQL은 어떻게 묶는가?** A. Force Matching Signature와 module/action을 사용한다. | parse calls/executions, parse time CPU, library cache 대기, Force Matching Signature, version_count | 여러 SQL_ID가 동일 서명으로 합쳐지는 전/후 표를 제공. `SQL_ID 1개 찾기` 답안은 부분점수만 부여 |
| **9. Redo 지표** | Redo size가 높으면 곧 Redo 로그가 작거나 LGWR가 느리다고 판단한다. commit/s와 `log file sync`, `log file parallel write`의 관계를 혼동한다. “커밋은 적을수록 무조건 좋다”고 생각한다. | **Q. Redo 54MB/s만으로 LGWR 병목인가?** A. 아니다. commit/s, sync latency, parallel write, 처리량을 함께 본다. **Q. 커밋 단위 확대의 위험은?** A. Undo·롤백량·락 유지시간 증가다. | redo size/s, commit/s, sync latency, parallel write latency, 업무 TPS, commit batch | 100→5,000건 조치의 효과와 위험·1,000건 롤백 조건을 한 세트로 작성하게 함 |
| **10. TOP SQL 기여도** | DB Time 1위 SQL 하나가 곧 유일 원인이라고 본다. SQL_ID 파편화, module/action, plan hash를 놓치고 누적값과 실행당 값을 혼합한다. DB Time과 elapsed를 더해 이중 합산한다. | **Q. 왜 SQL_ID 하나가 아니라 SQL군을 보는가?** A. 리터럴로 SQL_ID가 분산되기 때문이다. **Q. 책임 작업 입증 기준은?** A. 같은 장애 구간에서 SQL군의 DB Time·ASH 샘플·CPU/Reads·실행당 자원과 플랜을 연결한다. | SQL DB Time 기여율, ASH 샘플 74%, Force Matching Signature, module/action, plan hash, per-exec 지표 | SQL_ID별 표와 SQL군 집계표를 순차 공개. 74%가 어떻게 구성되는지 계산하게 하고 범위·구간을 명시 |

### 반복 질문으로 고정할 6문장

강사와 워크북은 수강생이 수치 하나로 단정할 때 아래 순서로 되묻는다.

1. **그 수치의 단위와 집계 구간은 무엇인가요?**
2. **비교한 정상 기준선은 같은 요일·시간·업무 상태인가요?**
3. **절대량, 비율, 실행당 값 중 무엇을 보고 있나요?**
4. **무엇이 먼저 변했고, 무엇이 뒤따랐나요?**
5. **ASH·SQL군·실행계획 중 책임 작업에 귀속시키는 증거는 무엇인가요?**
6. **제안 조치의 부작용과 롤백 조건은 무엇인가요?**

## 3. 4회차 현장 질의응답 운영 포인트

### A. 시작 전(00:00~00:15): 선수지식 오진 탐지

진단퀴즈에는 아래 5개 문항을 반드시 포함한다.

- AAS 12, 8코어라는 정보만으로 CPU 병목을 확정할 수 있는가?
- Buffer Hit 91%이면 Buffer Cache 증설이 1순위인가?
- Wait Event 1위가 항상 근본 원인인가?
- `E-Rows`와 누적 `A-Rows` 비교 시 `Starts`를 어떻게 반영하는가?
- Redo size 상승과 commit 병목은 같은 의미인가?

**운영 기준:** 5개 중 3개 이하 정답인 수강생은 팀 내 ‘질문자/검증자’ 역할을 먼저 맡기고, 공식·단위 치트시트를 제공한다. 이는 낙인 표시가 아니라 팀이 놓치기 쉬운 가정을 확인하는 역할로 안내한다.

### B. 프레임·시연(00:15~01:25): 설명보다 판단 언어 교정

- “원인은 CPU입니다”라고 답하면 → **“CPU는 자원 현상입니다. 어떤 작업이 언제부터 CPU를 썼나요?”**
- “디스크가 느립니다”라고 답하면 → **“요청량과 latency 중 무엇이 먼저 올랐고, OS 수치는 같은가요?”**
- “메모리를 늘리면 됩니다”라고 답하면 → **“어느 메모리이며, spill한 SQL과 증설 위험은 무엇인가요?”**
- “이 SQL이 1위입니다”라고 답하면 → **“SQL_ID가 분산되지 않았는지 어떤 키로 묶었나요?”**
- “통계를 수집하면 됩니다”라고 답하면 → **“pending stats·대표 데이터·롤백 방법 없이 운영 통계를 덮어써도 되나요?”**

강사는 정답을 바로 말하기보다 **다음에 열어볼 데이터 위치**를 질문으로 안내한다. 단, 3분 이상 팀이 멈추면 아래 힌트 단계로 개입한다.

### C. 발표·피드백(03:30~03:55): 반박은 사람 아닌 증거에

발표 후 다른 팀은 아래 중 하나만 질문한다.

- **범위 반박:** 같은 인스턴스/PDB/서비스·같은 구간인가?
- **시간 반박:** 원인이라고 한 지표가 실제로 먼저 변했는가?
- **귀속 반박:** ASH·SQL군·플랜이 같은 작업을 가리키는가?
- **조치 반박:** 위험·롤백·효과 검증 지표가 있는가?

“틀렸다” 대신 **“그 결론을 지지하는 두 번째 독립 증거는 무엇인가요?”**라는 문장을 사용하도록 발표 규칙에 명시한다.

## 4. 권장 팀 활동 방식

### 팀 구성과 역할

기본은 **3인 1조**, 인원상 불가하면 2인 1조로 운영한다.

| 역할 | 담당 | 역할 교대 시점 |
|---|---|---|
| **관찰자(Observer)** | 10개 지표의 단위·기준선·변화 시각을 기록하고 B0/T1~T4/R1을 표시 | Observe 종료 후 |
| **추적자(Investigator)** | AWR→ASH→SQL군→XPLAN을 연결하고 반증 자료까지 찾음 | Narrow 종료 후 |
| **검증자/브리퍼(Challenger)** | 임계값 단정·단위 혼합·인과 역전을 점검하고 조치 위험·롤백을 발표 | Prove 종료 후 |

2인 조는 관찰자와 추적자를 나누고, 검증자 체크리스트를 두 사람이 교차 서명한다. 역할은 실력 순으로 고정하지 말고 단계마다 교대해 특정 수강생에게 SQL 분석이 몰리지 않게 한다.

### 실습 B 권장 진행: 증거 퍼즐 + 단계별 공개

1. **Observe 15분:** 10개 지표 카드만 제공. 팀은 기준선과 최초 변화(T1)를 표시하고 병목 축을 최대 2개로 분류한다.
2. **Narrow 20분:** AWR/ASH 자료 공개. SQL_ID 단일 집계와 Force Matching Signature 집계를 비교해 책임 SQL군을 정한다.
3. **Prove 20분:** XPLAN·MEMSTATS 공개. 최초 카디널리티 오차 노드, 최대 Buffers/Reads 노드, spill 노드를 표시한다.
4. **Act 15분:** 즉시조치 2개와 근본조치 2개를 선택하고 각각 효과·위험·롤백 조건을 작성한다.
5. **보고 5분:** “현상 1문장–원인 2문장–증거 3개–조치/위험 2개” 형식으로 리허설한다.

각 단계 산출물을 제출해야 다음 데이터가 열리는 구조로 설계한다. 다만 느린 팀이 뒤처지지 않도록 정답 여부가 아니라 **최소 기록 요건 충족**으로 공개한다.

### 팀 상호검증 체크리스트

- [ ] 모든 수치에 단위·시간 구간·범위가 있다.
- [ ] 정상 기준선과 장애 구간이 같은 업무 조건이다.
- [ ] 비율만이 아니라 절대량 또는 실행당 수치가 있다.
- [ ] 원인 지표가 결과 지표보다 같거나 먼저 변했다.
- [ ] AWR·ASH·XPLAN 중 3개 층의 증거가 연결된다.
- [ ] SQL_ID 파편화를 SQL군으로 재집계했다.
- [ ] 즉시조치와 근본조치가 분리되어 있다.
- [ ] 각 조치에 위험·롤백·조치 후 검증 지표가 있다.

## 5. 난이도 조정안

### 공통 원칙

난이도는 기술 용어 설명을 늘리는 방식보다 **데이터 공개량, 계산 보조, 가설 수, 시간 압박**으로 조정한다. 핵심 학습목표인 증거 연결과 위험 포함 조치는 어느 수준에서도 제거하지 않는다.

| 수준 | 적용 대상·신호 | 제공 지원/변경 | 유지할 수행 기준 |
|---|---|---|---|
| **지원형(Level 1)** | 진단퀴즈 70% 미만, 단위 혼동, 5분 이상 첫 분석을 시작하지 못함 | 지표를 5개씩 두 묶음으로 공개, 공식·용어 카드 제공, T1 경계 표시, SQL군 후보 3개 제시, XPLAN 병목 후보 행 음영 표시 | 기준선 비교, 선후관계 1개, AWR·ASH·XPLAN 근거 각 1개, 조치 위험 1개 |
| **표준형(Level 2)** | 기본 운영안의 주 대상 | 10개 지표 전체, B0 범위만 제공, SQL_ID/서명 집계는 직접 비교, XPLAN 원본 제공 | 최소 3개 독립 수치 근거, SQL군 귀속, 즉시/근본조치와 롤백 조건 |
| **도전형(Level 3)** | 표준 과제를 15분 이상 일찍 끝냄, 근거 연결이 정확함 | 정상적인 잡음 SQL 추가, 5분 피크가 1시간 평균에 희석된 AWR 제공, 서로 다른 plan hash와 반증용 storage 지표 추가, RAC/PDB 범위 혼합 함정 1개 제공 | 오탐 제거 근거, 데이터 범위 정합성, 대안 가설 기각, 조치 후 검증 설계 |

### 3단계 힌트 규칙

1. **방향 힌트:** “09:30 전후 가장 먼저 변한 지표를 찾으세요.”
2. **위치 힌트:** “Hard Parse와 Force Matching Signature 표, ASH module 열을 함께 보세요.”
3. **구조 힌트:** “리터럴 SQL군 → CPU, MERGE의 A/E Rows 오차 → Reads/TEMP, commit/s → sync의 세 갈래로 연결해 보세요.”

힌트 사용은 감점하지 않고 기록만 한다. 파일럿에서는 팀별 힌트 단계·요청 시각을 수집해 콘텐츠 난이도 결함을 찾는다.

### 시간 부족 시 축소 순서

- **축소 가능:** 이벤트 정의 재강의, SQL 문법 작성, 차트 꾸미기, 팀별 발표 수(갤러리 워크로 대체)
- **축소 금지:** 기준선 비교, 선후관계 판정, SQL군 귀속, XPLAN 증명, 조치 위험·롤백 작성

## 6. 후속 콘텐츠 제작 필수 반영사항

1. **슬라이드:** 10개 지표를 개별 정의로 나열하기보다 `현상(AAS)–자원(CPU/I/O/PGA)–행동(Parse/Redo)–책임(TOP SQL)`의 관계도로 먼저 제시한다.
2. **워크북:** 모든 답안 칸을 `관찰/가설/확인 증거/판정` 4열로 만들고, 수치마다 단위·구간·범위 입력란을 둔다.
3. **데이터 팩:** 1분 버킷 원본, SQL_ID별 표와 Force Matching Signature 집계표, `ALLSTATS LAST +MEMSTATS +IOSTATS`, OS/storage 비교 자료를 포함한다.
4. **정답 해설:** 정답뿐 아니라 대표 오답 6종(AAS=CPU, Wait 1위=원인, Hit%=증설, latency=스토리지, Redo=LGWR, SQL_ID 1개=범인)과 반박 질문을 싣는다.
5. **평가:** 임계값을 맞힌 점수보다 **시간 선후관계, SQL군 귀속, 독립 증거, 위험·롤백**에 배점을 둔다. 근거 없는 정답 추측은 원인 항목의 절반을 넘지 못하게 한다.
6. **강사 가이드:** 각 실습 단계의 개입 시점(3분 정체), 3단계 힌트, 정서적으로 안전한 반박 문장, 빠른 팀용 도전 카드를 포함한다.
7. **표현 교정:** 기존 1~3회차의 “AAS<코어=안전”, “Hit 95% 이상 정상”, “Soft Parse 99.9% 절대” 같은 문구를 4회차에서 **범용 조치선이 아닌 참고치**로 명시적으로 재구성한다.

## 7. 파일럿에서 수집할 운영 지표

- 팀별 Observe/Narrow/Prove/Act 완료 시각과 전체 완주율(목표 **80% 이상**)
- 지표별 질문 빈도와 3단계 힌트 사용률
- 대표 오개념 6종의 사전·Exit Ticket 정답률 변화
- 팀 내 발언 편중 여부(한 사람이 분석·발표를 모두 수행했는지)
- 1페이지 보고서에서 단위·구간·범위 누락률
- 조치안의 위험·롤백 조건 포함률
- 난이도 체감 5점 척도와 자유 의견: “가장 막힌 지점 / 도움이 된 자료 / 불필요한 자료”

**난이도 조정 판단:** 동일 지점에서 팀의 40% 이상이 Level 2 힌트까지 요청하면 개인 역량보다 콘텐츠 단서 부족으로 보고 자료를 수정한다. 반대로 70% 이상이 힌트 없이 15분 이상 조기 완료하면 도전형 잡음 데이터 또는 반증 과제를 표준안에 일부 편입한다.
