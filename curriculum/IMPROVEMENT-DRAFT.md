## 1. 리스크 및 해석 전제 (먼저 밝힘)

- **학습자 정보 부재**: 학습자 수준/사전지식/명단 문서가 없어 "학습자 적합성"은 커리큘럼에 명시된 *대상/선수과정* 기술만으로 간접 평가함. 정량 근거는 없음.
- **SoT 이원화 리스크**: 커리큘럼 상태의 원천이 `ROADMAP.md`(문서)와 `academy.js`(코드) 두 곳에 있고 **서로 어긋나 있음**(§2-A). 개선 시 한쪽만 고치면 재발함.
- **UI 검증 제약**: `INSTRUCTIONS.md`상 에이전트의 브라우저 테스트가 금지되어, 화면 반영은 사용자 수동 확인이 필요.

## 2. 빠른 개선 (Quick Wins) — 저비용·즉효

### QW-1. 로드맵 상태값 SoT ↔ 구현 불일치 해소
- **현재 문제**: 과정 상태가 문서와 코드에서 다르게 표기됨.
  - `ROADMAP.md:38` SQL 튜닝 기본 = **기획 완료**, 하지만 `assets/js/academy.js:22` = `status: "live"`. 게다가 실제 학습자료 `assets/lessons/sql-tuning-basics/ch1~7.md`, `ap.md`가 이미 존재 → 사실상 운영 중.
  - `ROADMAP.md:36`(트랙 A L1 SQL기초=운영 중)은 맞으나, `ROADMAP.md:38`의 SQL튜닝 기본 "기획 완료" 표기가 코드/자료와 어긋남.
  - `curriculum/tuning/01-sql-tuning-basics.md:5` "상태: 기획 완료(구현 대기)" ← 학습자료가 이미 구현되어 있어 **낡은 상태값**.
- **제안**: `ROADMAP.md`와 각 과정 md의 상태 헤더를, 실제 구현(academy.js `status` + `assets/lessons` 존재)에 맞춰 **운영 중/기획 완료/기획**으로 일치시킨다. 상태 판정 기준(자료+랩+퀴즈 존재=운영 중)을 ROADMAP 범례에 명문화.
- **기대 효과**: 학습자 혼란 제거, 팀 내 진행상황 오판 방지, 이후 자동 동기화의 기준선 확보.
- **우선순위**: 높음 · **적용 난이도**: 하(문서 몇 줄 수정) · **선행 조건**: 각 과정의 "운영 중" 판정 기준을 팀이 1회 합의.

### QW-2. 자격증 표현 금지 규칙 위반 시정
- **현재 문제**: `INSTRUCTIONS.md`/`STRUCTURE.md`가 **자격증(SQLD/SQLP) 표현 금지**를 명시했는데, `assets/js/academy.js:52-56` 비정규 스터디에 `"SQLD 취득!"`, `sub: "자격증 취득 스터디"` 카드가 노출됨.
- **근거**: `INSTRUCTIONS.md` "⚠️ 자격증(SQLD/SQLP 등) 표현 금지", `STRUCTURE.md` 핵심 원칙 3, vs `assets/js/academy.js:52-56`.
- **제안**: 두 가지 중 택1을 팀이 결정 —
  1) 규칙을 정규과정에만 한정한다고 판단하면 `INSTRUCTIONS.md`에 "비정규 스터디는 예외" 문구 추가(규칙 현실화), 또는
  2) 규칙 유지 시 카드 명칭을 역량 기준(예: "SQL 개발자 자격 대비 스터디" 대신 "SQL 실무 기본기 스터디")으로 변경.
- **기대 효과**: 지침-구현 모순 제거, 브랜딩 일관성.
- **우선순위**: 높음 · **적용 난이도**: 하 · **선행 조건**: 규칙 적용 범위(정규/비정규) 팀 확정.

### QW-3. 비정규 스터디의 문서 근거 부재 보완
- **현재 문제**: `academy.js:49-79`에 비정규 스터디 4종(성능진단 소모임/SQLD/클라우드DB(MySQL)/SQL튜닝) + CBT + 찾아가는 기술서비스 카드가 있으나, `curriculum/`에는 **성능진단 소모임만** 문서화(`study-performance-club.md`)됨. 나머지는 커리큘럼 근거 없음.
- **근거**: `assets/js/academy.js:57-77` vs `curriculum/` 디렉터리에 해당 스터디 md 부재.
- **제안**: 각 비정규 스터디에 대해 `study-performance-club.md`와 동일 포맷의 **1페이지 개요 md**(대상/목표/세션/실습/상태)를 `curriculum/`에 추가. 최소한 목표·세션 목차만이라도 SoT화.
- **기대 효과**: 스터디 운영의 목표/범위 명문화, 신규 참여자 온보딩 자료 확보.
- **우선순위**: 중 · **적용 난이도**: 하~중(문서 신규 작성) · **선행 조건**: 각 스터디 운영자로부터 목차·목표 수집.

### QW-4. SQL 기초 → 튜닝 트랙 연결 고리 명시 강화
- **현재 문제**: `foundation/sql-foundation.md:20` 세션6이 "실행계획 살짝 보기(→튜닝 트랙 연결)"로 연결을 예고하나, 어떤 랩/개념으로 이어지는지 구체 앵커가 없음. 반면 튜닝 과정은 1장부터 실행계획 시각화(`panel-explain`)를 사용.
- **근거**: `foundation/sql-foundation.md:20` vs `tuning/01-sql-tuning-basics.md` 1장 랩.
- **제안**: SQL 기초 세션6 항목에 "다음 과정에서 `panel-explain`로 확장" 식의 명시적 브릿지 문장 1줄 추가(문서만).
- **기대 효과**: 트랙 전환 시 학습 단절 완화, 선수-후속 연계 인지 향상.
- **우선순위**: 중 · **적용 난이도**: 하 · **선행 조건**: 없음.

## 3. 중장기 개선 (Structural) — 설계·운영 개선

### LT-1. 상태 SoT 단일화 및 자동 동기화
- **현재 문제**: 상태 원천이 `ROADMAP.md`(문서)와 `academy.js`(코드)로 이원화되어 QW-1 같은 불일치가 구조적으로 재발함. `STRUCTURE.md` 핵심 원칙 1도 "항상 일치시킨다"는 *수기 규율*에 의존.
- **근거**: `ROADMAP.md`(상태표) ↔ `assets/js/academy.js`(ACADEMY.tracks `status`) 이중 관리.
- **제안**: 커리큘럼 메타(과정명/레벨/상태/course-id/enter-id)를 `curriculum/roadmap.json` 한 파일로 두고, ① academy.js가 이를 fetch해 렌더 ② ROADMAP.md는 이 json에서 생성/검증하는 스크립트를 CI/로컬에 추가.
- **기대 효과**: 불일치 원천 제거, 신규 과정 추가 시 한 곳만 수정.
- **우선순위**: 높음(반복 비용 큼) · **적용 난이도**: 중 · **선행 조건**: QW-1 선(先) 정합화, 데이터 스키마 합의, UI 회귀는 사용자 수동 확인.

### LT-2. 과정 간 랩 소유권·중복 정리 (정규화 변환기 등)
- **현재 문제**: "정규화 변환기" 랩의 소유권이 두 과정에 걸쳐 있고, 문서가 스스로 "확인 필요"라고 남겨둠.
  - `design/01-data-modeling.md`(3장 신규 핵심 랩, "고성능 DB 설계가 🔗 공유") 와 `design/02-highperf-db-design.md`(세션1 실습 = 정규화 변환기 "신규")가 **동일 랩을 각기 신규/재사용으로 상이 표기**.
  - `01-data-modeling.md`의 "경계/소유권 메모(확인 필요)"에 중복 제작 방지 권고가 이미 적혀 있음.
- **근거**: `design/01-data-modeling.md`(정규화 변환기 신규 + 경계/소유권 메모) vs `design/02-highperf-db-design.md`(세션1 표 "신규").
- **제안**: 랩 소유권 매트릭스(랩 id → 원소유 과정 → 재사용 과정)를 `curriculum/` 또는 `STRUCTURE.md`의 "과정 인벤토리" 표에 컬럼 추가로 확정. 02는 "정규화 변환기 = ♻️ data-modeling 재사용, 물리화/성능 관점만 추가"로 명문화.
- **기대 효과**: 중복 제작 공수 절감, 랩 유지보수 단일화.
- **우선순위**: 중 · **적용 난이도**: 중 · **선행 조건**: data-modeling ↔ highperf-db-design 범위 경계(이미 두 md에 초안 존재) 팀 승인.

### LT-3. 난이도 곡선·선수지식 브릿지 보강 (SQL 튜닝 기본)
- **현재 문제**: `tuning/01-sql-tuning-basics.md`는 「친절한 SQL 튜닝」 7장+부록을 그대로 골격으로 채택. 1장(파싱/최적화/I·O 이론) → 4장(NL/소트머지/해시 조인) → 7장(옵티마이저 통계·비용)로 이어지는 구간에서 **이론 밀도가 급격히 상승**. SQL 기초의 출력은 SELECT 작성/결과 예측 수준(`sql-foundation.md` 목표)이라 실행계획·비용모델 사전지식 격차 존재.
- **근거**: `foundation/sql-foundation.md`(목표: 정확한 SELECT 작성) vs `tuning/01-sql-tuning-basics.md` 1장·7장(옵티마이저 비용/통계 이론).
- **제안**: (a) 1장 앞에 "실행계획 읽는 법" 15분짜리 온램프(SQL기초 세션6과 연속) 삽입, (b) 각 장 도입부에 "이 장에 필요한 선수 개념" 박스 추가(문서), (c) 랩 우선(hands-on) → 이론 심화 순으로 장 내 순서 권고.
- **기대 효과**: 중도 이탈 감소, 이론 급상승 완충.
- **우선순위**: 중 · **적용 난이도**: 중(학습자료 편집) · **선행 조건**: 실제 lesson md(`assets/lessons/sql-tuning-basics/ch*.md`) 내용 상세 리뷰(본 초안 범위 밖, 후속 조사 필요).

### LT-4. 평가(퀴즈/CBT)와 학습목표의 매핑 명시
- **현재 문제**: 각 과정 md에 "장별 미니 퀴즈 + 종합 퀴즈"가 있고 별도 CBT(`generate_cbt.py`, academy.js `cbt` 노드)가 있으나, **어떤 학습목표(LO)를 어떤 문항이 검증하는지 매핑이 없음**. 평가 타당성 근거가 문서화되지 않음.
- **근거**: `foundation/sql-foundation.md`(세션별 퀴즈 열)·`tuning/01-sql-tuning-basics.md`(퀴즈 섹션)에 목표-문항 연결 표 부재; `generate_cbt.py` 존재.
- **제안**: 과정별로 "학습목표 → 평가문항(퀴즈/CBT) 커버리지 표"를 추가. 미커버 목표/과잉 문항을 가시화. CBT 문항에 대상 목표 태그 필드 도입.
- **기대 효과**: 평가 타당성 확보, 사각지대(가르쳤지만 평가 안 함/평가하지만 안 가르침) 발견.
- **우선순위**: 중 · **적용 난이도**: 중~상 · **선행 조건**: `generate_cbt.py` 문항 데이터 구조 조사(후속), 학습목표를 LO 코드로 정형화.

### LT-5. 학습자 프로파일/사전진단 도입
- **현재 문제**: 학습자 명단·수준·이력 문서가 전무(§0). "대상/선수과정"이 문서에 기술돼 있으나 실제 학습자 매칭 근거 없음 → 학습자 적합성 판단 불가.
- **근거**: `curriculum/**`에 학습자 관련 문서 부재(전체 탐색으로 확인).
- **제안**: (a) 과정 진입 전 5문항 사전진단(선수지식 체크) 미니 랩 추가, (b) 익명 집계로 난이도 조정 근거 수집(기존 방문 집계 인프라 `/tsclass/__visit` 패턴 재사용 가능).
- **기대 효과**: 데이터 기반 난이도/순서 조정, 적합성 평가의 정량 근거 확보.
- **우선순위**: 낮음(가치 높으나 선행 많음) · **적용 난이도**: 상 · **선행 조건**: 개인정보/집계 정책 확인, 서버 로깅 인프라 확장.
