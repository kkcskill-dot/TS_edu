# 실행 계획(Execution Plan) 분석 가이드

## 1. 실행 계획(Execution Plan)이란?

실행 계획은 Oracle 옵티마이저(Optimizer)가 SQL 문을 가장 효율적으로 실행하기 위해 세운 절차와 방법을 시각적으로 표현한 것이다.
개발자는 실행 계획을 통해 SQL 성능 문제의 원인을 파악하고 튜닝의 방향을 결정할 수 있다.
본 가이드는 개발자가 실행 계획을 효과적으로 분석하고 활용하는 방법을 안내한다.

* 테이블 전체를 스캔하는지(`Full Table Scan`), 인덱스를 사용하는지(`Index Scan`) 등을 파악한다.
* 테이블 조인 순서와 방식(`Nested Loops`, `Hash Join` 등)을 확인하여 효율성을 점검한다.
* 각 단계별 예상 비용(Cost)과 처리 건수(Cardinality)를 분석하여 비효율적인 지점을 찾는다.

실행 계획은 일종의 "내비게이션 경로"와 같다. 목적지(결과)를 향해 어떤 길(연산)을 선택했는지 명확하게 보여준다.

---

## 2. 핵심 오퍼레이션 요약

* **TABLE ACCESS FULL**: 전체 테이블 스캔 (처리 속도 느림)
* **INDEX RANGE SCAN**: 인덱스를 활용한 범위 검색 (처리 속도 빠름)
* **NESTED LOOPS**: 루프를 돌며 조인 (소량 데이터 처리에 적합)
* **HASH JOIN**: 해시 테이블을 생성하여 조인 (대량 데이터 처리에 적합)
* **COST**: Oracle 옵티마이저가 판단한 상대적 비용 (수치가 낮을수록 효율적임)

---

## 3. 실제 쿼리 플랜 확인 방법

INDEX RANGE SCAN을 의도했지만 INDEX SKIP SCAN이 발생하는 경우 등, 실제 쿼리의 플랜을 점검하는 절차는 다음과 같다.

```sql
-- 1. 통계 수집 레벨 설정
ALTER SESSION SET STATISTICS_LEVEL = ALL;
 
-- 2. 실제 쿼리 수행 (GATHER_PLAN_STATISTICS 힌트 및 식별용 주석 추가)
SELECT /*+ GATHER_PLAN_STATISTICS */    /* TEST_QUERY */
       A.SALE_DT, A.BILL_NO
  FROM SA0100M A
 WHERE A.COMP_CD = '01'
   AND A.SALE_STOR_CD = '08'
   AND TO_DATE(A.SALE_DT, 'YYYYMMDD') BETWEEN SYSDATE - 1 AND SYSDATE;
 
-- 3. 주석을 이용해 쿼리의 SQL_ID 찾기
SELECT /*+ PARALLEL(A 8) */ SUBSTR(SQL_TEXT, 1, 30) AS SQL_TEXT, MODULE, PARSING_SCHEMA_NAME, SQL_ID
  FROM V$SQLAREA A
 WHERE SQL_TEXT LIKE '%TEST_QUERY%'
 ORDER BY FIRST_LOAD_TIME DESC;
 
-- 4. SQL_ID를 통한 실제 플랜 확인
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR('추출한_SQL_ID', NULL, 'IOSTATS COST LAST'));
```

**출력 예시**:
```text
--------------------------------------------------------------------------------------------------------------------------------
| Id  | Operation                    | Name            | Starts | E-Rows | Cost (%CPU)| A-Rows |   A-Time   | Buffers | Reads  |
--------------------------------------------------------------------------------------------------------------------------------
|   0 | SELECT STATEMENT             |                 |      1 |        |   652 (100)|      0 |00:00:02.23 |    4797 |   4791 |
|*  1 |  FILTER                      |                 |      1 |        |            |      0 |00:00:02.23 |    4797 |   4791 |
|   2 |   TABLE ACCESS BY INDEX ROWID| SA0100M         |      1 |   3291 |   652   (1)|      0 |00:00:02.23 |    4797 |   4791 |
|*  3 |    INDEX SKIP SCAN           | IDX_SA0100M_010 |      1 |    107 |   648   (1)|      0 |00:00:02.23 |    4797 |   4791 |
--------------------------------------------------------------------------------------------------------------------------------
```

> **주의사항**: 인덱스로 사용할 WHERE 절 컬럼에 가공(함수 적용 등)이 이뤄지면 의도한 인덱스를 타지 않을 수 있다. 플랜을 통해 의도대로 스캔이 진행되었는지 반드시 확인해야 한다.

## 4. DBMS_XPLAN.DISPLAY_CURSOR 포맷(FORMAT) 옵션

* **TYPICAL**: 기본값. 예상 행 수, 비용 등 주요 정보만 출력한다.
* **ALL**: 가능한 모든 정보(예상/실제 행 수, 메모리 사용 등)를 출력한다.
* **ALLSTATS**: 실제 실행 통계(실제 행 수, 반복 횟수 등)를 포함한다. `GATHER_PLAN_STATISTICS` 힌트와 병행해야 효과적이다.
* **LAST**: 반복 실행된 커서 중 마지막 실행 기준의 실제 통계만 출력한다.
* **ADVANCED**: 병렬 실행, 메모리 분배 등 고급 정보를 포함한다.
* **IOSTATS**: 버퍼 읽기, 디스크 읽기 등 I/O 관련 통계를 포함한다.
* **MEMSTATS**: 메모리 사용 통계를 포함한다.
* **PARALLEL**: 병렬 실행 관련 정보를 포함한다.
* **ALIAS**: 테이블 별칭 정보를 포함한다.
* **NOTE**: Oracle이 제공하는 튜닝 관련 힌트나 주석을 포함한다.
* **COST**: CPU COST를 포함한다.

---

## 5. 복잡한 실행 계획 읽는 법

실행 계획은 가장 안쪽에 들여쓰기(Indentation) 된 작업부터 시작하여 바깥쪽으로 해석한다.

1. **가장 안쪽 우선**: 가장 안쪽으로 들여쓰기 된 작업이 가장 먼저 실행된다.
2. **동일 레벨 위쪽 우선**: 같은 들여쓰기 레벨에서는 위에 위치한 작업이 먼저 실행된다. 이 작업을 'Outer' 또는 'Driving' 테이블이라 부르며, 이 작업의 결과 1건(Row)마다 아래쪽(Inner) 작업을 반복 수행한다.

## 6. 실행 계획 분석 7단계 가이드

### 1단계: 비효율적인 Full Table Scan 확인
* **점검 항목**: `Operation` 컬럼에 `TABLE ACCESS FULL`이 나타나는지 점검한다.
* **분석**: 대용량 테이블의 Full Scan은 성능 저하의 주원인이다. WHERE 절에 인덱스가 없거나, 함수 가공 등으로 인덱스를 사용할 수 없는 형태(SARG 위반)일 때 발생한다.
* **사례 (함수 사용 및 묵시적 형변환)**:
  * 인덱스 컬럼에 `TO_DATE` 등 함수를 씌우면 Full Scan이 발생한다. 컬럼을 가공하지 말고 값 범위를 설정해야 한다. (예: `SALE_DT >= TO_CHAR(...)`)
  * `VARCHAR2` 타입 컬럼에 숫자 값을 대입하면 묵시적 형변환(`TO_NUMBER`)이 발생하여 인덱스가 무력화된다. 타입에 맞게 조회 값을 변경해야 한다.
* **SARG(검색 인수) 위반 주요 사례**: 컬럼에 연산 적용, `LIKE '%VALUE'` 앞부분 와일드카드 사용, 데이터 타입 불일치 등.

### 2단계: 옵티마이저 예측 정확도(Cardinality) 확인
* **점검 항목**: 조인 시 `NESTED LOOPS`, `HASH JOIN` 중 어떤 방식이 사용되는지 점검한다.
* **분석**: 옵티마이저가 데이터 건수를 잘못 예측하면 비효율적 조인을 선택한다. 통계 정보 노후화나 연관된 컬럼 조회 시 독립 계산 오류로 인해 발생한다.
* **해결 방안**: DB 담당자에게 통계 정보 재생성(`DBMS_STATS.GATHER_TABLE_STATS`)을 요청하거나 확장 통계를 생성한다.

### 3단계: 조인 방식(Join Method) 및 순서 확인
* **점검 항목**: `Rows` 예측치와 실제 건수를 비교하고, 조인 순서(Driving Table)를 점검한다.
* **분석**: 데이터가 적은 테이블에서 많은 테이블 방향으로 조인하는 것이 유리하다. 순서가 반대이거나 조인 조건 누락으로 인한 `Cartesian Product`(전체 건수 곱연산)가 발생했는지 확인해야 한다.
* **해결 방안**: `LEADING`이나 `ORDERED` 힌트를 사용하여 최적의 순서를 지정하고 누락된 조인 조건을 추가한다.

### 4단계: 불필요한 작업 및 필터링 위치 확인
* **점검 항목**: 불필요한 `SORT`나 비효율적인 `filter` 오퍼레이션이 있는지 점검한다.
* **분석**: `filter(...)`는 전체 데이터를 읽은 후 버리는 작업으로 비효율적이다.
* **사례**:
  * 중복 제거가 불필요한 상황에서 `UNION`을 사용하면 비싼 `SORT (UNIQUE)` 연산이 발생한다. `UNION ALL`로 대체한다.
  * SELECT 절의 스칼라 서브쿼리는 메인 쿼리 건수만큼 반복 실행(FILTER)된다. 일반 JOIN 구문으로 변경하여 최적화를 유도한다.

### 5단계: WHERE 절 조건 최적화 (OR, NOT IN 등)
* 인덱스가 있는 두 컬럼을 `OR`로 연결하면 풀 스캔이 발생할 수 있다. `UNION ALL`로 분리하여 각 쿼리가 인덱스를 타게 한다.
* `NOT IN` 서브쿼리 결과에 `NULL`이 포함되면 쿼리가 오류 없이 0건을 반환하는 문제가 생기며 안티 조인 비효율이 발생한다. `NOT EXISTS` 사용이 성능과 논리적 안정성 면에서 우수하다.

### 6단계: 인덱스 활용 극대화 (결합 인덱스와 Covering Index)
* **결합 인덱스 선행 컬럼**: `(COL1, COL2)` 인덱스에서 선행 컬럼 `COL1` 조건이 빠지면 `Index Full Scan`이나 `Index Skip Scan` 같은 비효율적 탐색이 발생한다. 조회 패턴에 맞는 인덱스 재설계가 필요하다.
* **Covering Index**: 쿼리에서 요구하는 모든 컬럼이 인덱스에 포함되어 있으면, 테이블 블록 접근(`TABLE ACCESS`) 없이 `INDEX RANGE SCAN`만으로 결과를 반환하여 I/O 비용이 대폭 절감된다.

### 7단계: VIEW MERGING 실패 점검
* 단순 View는 기반 테이블과 병합(Merging)되어 쿼리가 최적화되나, `GROUP BY`, `DISTINCT`가 포함된 복잡한 View는 독립 실행 후 조인되어 비효율을 낳는다.
* 실행 계획에 `VIEW` 오퍼레이션이 보인다면 병합에 실패한 것이다. 기반 테이블을 직접 조인하는 형태로 쿼리를 개편하거나 `/*+ MERGE */` 힌트를 고려해야 한다.
