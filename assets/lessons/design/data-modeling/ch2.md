# 2장. 개념 모델링

## 2.1 데이터 모델링 접근방법

개념 모델을 만드는 두 가지 방향이 있습니다. 실무에서는 **둘을 병행**합니다.

**하향식(Top-Down)** — 업무 요건에서 출발
- 업무를 분석해 핵심 **엔티티**를 먼저 도출 → 관계 → 속성 순으로 상세화
- 신규 시스템·업무 재설계에 적합
- 장점: 업무 규칙을 충실히 반영 / 단점: 현행 데이터와 괴리 가능

**상향식(Bottom-Up)** — 현행 데이터에서 출발
- 기존 화면·장표·테이블을 수집해 **통합**하며 엔티티를 정리
- 레거시 통합·차세대 전환에 적합
- 장점: 실데이터 근거 / 단점: 현행의 잘못된 구조를 답습할 위험

**주제영역(Subject Area)** — 큰 시스템은 한눈에 안 들어옵니다. 업무를 **주제영역**으로 분할해 정복합니다. 예) `고객`, `상품`, `주문/결제`, `배송`, `정산`. 주제영역 단위로 개념 모델을 그린 뒤 통합합니다.

## 2.2 개념 모델링

**개념 모델링**의 목표는 *상세 속성 이전에* 업무의 **뼈대**(핵심 엔티티와 관계)를 합의하는 것입니다.

**절차**
1. **핵심 엔티티 식별** — 업무에서 "관리 대상"이 되는 명사를 뽑는다
   - 후보: 고객, 상품, 주문, 결제, 배송 …
   - 검증: "이 대상의 목록을 따로 관리하는가? 식별자가 있는가?"
2. **관계 식별** — 엔티티 사이의 업무적 동사를 찾는다
   - 고객 **─(주문한다)─** 주문, 주문 **─(포함한다)─** 상품
3. **업무 규칙 정리** — 관계의 카디널리티·선택성을 문장으로 적는다
   - "한 고객은 0개 이상의 주문을 한다(1:N, 선택)"
   - "한 주문은 1개 이상의 상품을 포함한다(M:N → 다음 단계에서 해소)"
4. **개념 ERD 작성** — 엔티티 박스 + 관계선. 속성은 식별자 정도만.

**핵심 엔티티 vs 행위 엔티티 vs 그냥 속성** — 자주 헷갈립니다.
- `고객`은 엔티티(목록·식별자 있음)
- `주문`은 행위(이벤트) 엔티티(언제·누가·무엇을 = 업무 발생)
- `고객등급`은? → 코드성이면 **코드 엔티티**, 단순 구분값이면 **속성**

> 개념 단계에서는 **완벽함보다 합의**가 중요합니다. 이해관계자가 같은 그림을 보고 "맞다"고 동의하면 충분합니다. 상세화(속성·정규화)는 다음 장(논리 모델링)에서 합니다.

**예시 — 쇼핑몰 개념 모델(뼈대)**

```text
[고객] ──< 주문한다 >── [주문] ──< 포함한다 >── [상품]
                          │
                       < 결제된다 >
                          │
                       [결제]
```

- 고객 : 주문 = 1 : N
- 주문 : 상품 = M : N  → 논리 단계에서 **주문상품**(교차 엔티티)으로 분해
- 주문 : 결제 = 1 : 1 (또는 1:N, 부분결제 허용 시)

다음 장에서 이 뼈대에 **속성·식별자·정규화**를 입혀 논리 모델로 정밀화합니다.
