# 5장. 모델링 이야기 (실무 케이스)

이론은 같아도 현실은 케이스마다 다릅니다. 실무에서 자주 마주치는 설계 판단을 모았습니다. **정답보다 트레이드오프**를 이해하세요.

## 식별자 — 자연키 vs 인조(대리)키
- **자연키(Natural Key)**: 업무 의미가 있는 키(주민번호, 사업자번호). 의미 있으나 **변할 수 있고**(정책 변경) 길거나 민감
- **인조키(Surrogate Key)**: 시퀀스 등 무의미 키. 안정적·짧음, 그러나 **업무 유일성**은 별도 UNIQUE로 보장해야
- **언제 인조키?**: 자연키가 길거나·변하거나·복합으로 복잡할 때, 또는 다양한 업무발생(주문·접수·신청)처럼 발생 자체가 키일 때
- ⚠️ 인조키를 쓰더라도 **자연키 UNIQUE 제약**은 반드시 유지(중복 데이터 방지)

## 이력 관리 — 점 이력 vs 선분 이력
- **점 이력**: 변경 시점만 기록(`변경일시`). 특정 시점 상태 조회 시 "그 이전 최댓값"을 찾아야 해 **쿼리가 복잡**
- **선분 이력**: 유효 구간을 `시작일~종료일`로 기록. 특정일 조회가 `BETWEEN` 한 줄로 단순

```text
점 이력)  2024-01-01 등급=SILVER
          2024-06-01 등급=GOLD
  → "2024-03-01 등급?" : 03-01 이하 중 최근 행 탐색

선분 이력) 2024-01-01 ~ 2024-05-31  SILVER
          2024-06-01 ~ 9999-12-31  GOLD
  → "2024-03-01 등급?" : WHERE :d BETWEEN 시작일 AND 종료일
```

- 트레이드오프: 선분 이력은 조회가 쉽지만, 변경 시 **이전 행의 종료일을 갱신**해야(쓰기 로직 복잡). 실습 **「선분 이력 변환」** 참고.

## 문자열 데이터 분리(수직분할)
- 자주 안 쓰는 **대용량 컬럼**(비고·본문·이미지)을 별도 테이블로 분리 → 본체 행이 짧아져 I/O·캐시 효율↑
- 1:1 관계로 분리하고 PK 공유. "거의 항상 함께 조회"하면 분리가 오히려 손해(조인 비용)

## 공통코드 설계
- **통합 코드 테이블**(코드그룹+코드+코드명): 코드 추가가 데이터로 끝남(유연), 그러나 타입 통일·조인 증가
- **코드별 개별 테이블**: 명확·제약 강하나 코드 늘 때마다 테이블 추가
- 절충: 통합 코드 테이블 + 자주 쓰는 코드는 캐시. 코드값에 **의미 부여(0/1)** 는 지양(가독성)

## 개인정보 데이터 구조와 암호화
- 주민번호·계좌 등 민감정보는 **암호화 저장**. 단 암호화 컬럼은 **= 검색만**(범위·LIKE 불가, 인덱스 효과 제한)
- 검색용 **부분 인덱스 컬럼**(예: 생년월일·해시) 분리, 원문은 암호화 컬럼에 보관
- 최소 수집·분리 보관·접근 통제를 구조에 반영

## 과도한 통합 / 일반화의 함정 — "어디까지 통합할 것인가"
- 비슷한 엔티티를 하나로 합치면(고객·공급사·직원 → "거래처") 유연하지만, **NULL 폭증·제약 약화·쿼리 복잡**
- **데이터 통합 ≠ 구조 통합**: 값을 모으는 것과 한 테이블로 합치는 것은 다름
- 원칙: **공통 속성·공통 행위가 충분할 때만** 통합. 억지 일반화는 "원칙과 현실 사이"에서 현실을 택해야

## 참조 무결성 — 선언 vs 운영
- FK 제약을 **걸면** DB가 정합성을 보장하지만, 대량 적재·삭제 시 부담 → 운영 정책 필요
- ON DELETE: 제한(기본·안전) / CASCADE(부모 삭제 시 자식까지, 신중) / SET NULL
- FK를 안 거는 경우(성능·이관)에도 **무결성 책임은 사라지지 않음**(애플리케이션·배치로 보장)

## 순환관계 / 자기참조
- 카테고리 계층·사원-관리자처럼 자기 테이블 참조 → 입력 순서(부모 먼저)·삭제 정책 주의
- 계층 조회는 `CONNECT BY` 또는 재귀 CTE. 깊이가 깊으면 **경로(path) 컬럼** 반정규화 고려

## 엔티티 정의가 명확한가? — 모델링의 출발점
- "고객"의 정의가 사람마다 다르면 모델이 흔들립니다(가입자? 구매자? 수신자?)
- 각 엔티티에 **한 문장 정의 + 식별자 + 인스턴스 예시**를 명문화. 정의가 흐릿하면 통합·관계가 모두 틀어짐
