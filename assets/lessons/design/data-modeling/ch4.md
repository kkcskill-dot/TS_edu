# 4장. 물리 모델링

## 4.1 물리 모델링이란

**물리 모델링**은 논리 모델을 **특정 DBMS의 실제 객체**(테이블·컬럼·제약·인덱스·파티션)로 변환하는 단계입니다. 여기서부터 **성능·저장·운영** 요건을 반영합니다.

| 논리 | → | 물리 |
|---|---|---|
| 엔티티 | → | 테이블 |
| 속성 | → | 컬럼(+ 데이터 타입) |
| 식별자 | → | 기본키(PK) + 인덱스 |
| 관계 | → | 외래키(FK) |
| 도메인 | → | 타입·길이·CHECK |

## 4.2 테이블 설계

- **명명**: 표준 단어·복수/단수 규칙 일관 적용
- **슈퍼/서브타입 물리화** — 3가지 선택지(트레이드오프)
  - **단일 테이블(롤업)**: 슈퍼+서브를 한 테이블로(타입 컬럼 + NULL 많음). 조인 없음, 공간 낭비
  - **테이블 분리(롤다운)**: 서브타입별 테이블. 명확하나 공통 조회 시 UNION
  - **개별 + 공통**: 슈퍼 1 + 서브 N. 유연하나 조인 증가
- **행 길이**: 너무 넓은 테이블은 I/O·마이그레이션 부담 → 수직분할 고려(5장)

## 4.3 관계 설계

- **관계 → FK**: 부모 PK를 자식 FK로
- **식별 관계**: 부모 키가 자식 PK에 포함(예: 주문상품 PK = 주문번호+상품번호)
- **비식별 관계**: 부모 키가 자식의 일반 FK
- **M:N**: 교차 테이블로 구현(3장에서 분해한 결과)

## 4.4 컬럼 설계

- **데이터 타입**: 의미에 맞는 최소 타입. 과대 타입은 낭비·형변환 유발
  - 숫자는 `NUMBER`, 가변 문자열은 `VARCHAR2`, 일시는 `DATE`/`TIMESTAMP`
  - **숫자를 문자로 저장하지 말 것** → 조인·비교 시 암묵적 형변환으로 인덱스 무력화
- **NULL 설계**: NOT NULL을 적극 명시(옵티마이저·무결성에 유리)
- **기본값(DEFAULT)**: 상태·생성일시 등
- **컬럼 순서**: 자주 함께 쓰는 컬럼·고정폭을 앞쪽에(가독성·일부 저장 효율)

> 설계 안티패턴(과대 타입·형변환 유발·FK 누락)은 실습 **「플랜 진단」(재사용)** 에서 잘못된 타입이 인덱스를 어떻게 무력화하는지 확인할 수 있습니다.

## 4.5 데이터 무결성 설계

규칙은 가능하면 **선언적 제약**으로 DB가 강제하게 합니다(애플리케이션 코드보다 안전).

| 제약 | 보장 |
|---|---|
| **PK** | 유일 + NOT NULL(개체 무결성) |
| **FK** | 참조 대상 존재(참조 무결성) |
| **UNIQUE** | 대체키 유일성 |
| **NOT NULL** | 필수값 |
| **CHECK** | 값 범위·코드 도메인 |

```sql
CREATE TABLE order_item (
  order_id  NUMBER       NOT NULL,
  prod_id   NUMBER       NOT NULL,
  qty       NUMBER(9)    NOT NULL CHECK (qty > 0),
  CONSTRAINT pk_order_item PRIMARY KEY (order_id, prod_id),   -- 식별관계(복합 PK)
  CONSTRAINT fk_oi_order FOREIGN KEY (order_id) REFERENCES orders(order_id),
  CONSTRAINT fk_oi_prod  FOREIGN KEY (prod_id)  REFERENCES product(prod_id)
);
```

**참조 무결성 옵션**: FK의 ON DELETE 동작(제한/CASCADE/SET NULL)을 업무 규칙에 맞게 선택(5장 케이스).

## 4.6 성능을 고려한 데이터 구조

- **반정규화 물리 적용**: 측정된 병목에 한해 컬럼 중복·집계 컬럼·요약 테이블
- **이력 구조**: 점 이력 vs 선분 이력(5장에서 상세)
- **파티셔닝 후보 식별**: 대용량·기간성 테이블(로그·주문)은 파티션 키 후보를 표시

## 4.7 물리 설계 / 4.8 인덱스 설계 / 4.9 파티션 설계 (기본)

이 과정(L2)에서는 **모델 관점의 기본 원칙**까지 다룹니다. 저장구조·라이프사이클 **운영**은 다음 과정 *고성능 DB 설계*에서 심화합니다.

**인덱스 설계 기본**
- PK·UK는 자동 인덱스. 자주 쓰는 **검색·조인·정렬** 컬럼을 후보로
- **결합 인덱스 컬럼 순서**: 등치(=) 조건·선택도 높은 컬럼을 앞에
- 인덱스가 많을수록 **DML이 느려진다**(모든 인덱스 동시 갱신) → 과다 생성 주의

> 실습 **「인덱스 시뮬레이터」(재사용)** 로 결합 인덱스의 수직/수평 탐색과 컬럼 순서 효과를 확인하세요.

**파티션 설계 기본**
- 큰 테이블을 **파티션 키**로 분할(Range=기간, List=구분, Hash=분산)
- 효과: 프루닝(불필요 파티션 스캔 제외), 관리 단위 분리(오래된 파티션 일괄 삭제)
- **라이프사이클 운영**(Interval 자동 생성·만료 DROP·Exchange 적재)은 → *고성능 DB 설계*
