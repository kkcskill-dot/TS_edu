# 1회차: SQL기본, 플랜기본 + 옵티마이저의 착각과 쿼리 변환 제어

> 💡 **학습 목표**
> 옵티마이저가 쿼리를 어떻게 변환하는지(Query Transformation) 이해하고, 변환이 실패했을 때 벌어지는 실무적인 대참사와 그 우회 기법을 습득합니다.

---

## 1. 서브쿼리 Unnesting과 View Merging

### 서브쿼리 Unnesting (서브쿼리 풀어내기)
서브쿼리를 메인 쿼리와 합쳐서 조인(Join) 형태로 풀어내는 최적화 기법입니다. 옵티마이저가 더 많은 조인 경로와 순서를 평가할 수 있게 해줍니다.

> [!NOTE]
> **장애 사례: "어제까지 잘 돌던 쿼리가 갑자기 멈췄어요!"**
> - **원인**: 메인 쿼리와 서브쿼리가 Unnesting 되지 않고 `FILTER` 오퍼레이션으로 풀리면서, 메인 쿼리의 건수만큼 서브쿼리가 반복 수행(루프)되었기 때문입니다.
> - **해결**: `/*+ UNNEST */` 힌트를 사용하여 옵티마이저에게 명시적으로 조인으로 풀 것을 지시하거나, 쿼리를 일반 조인문으로 재작성합니다.

### View Merging (뷰 병합)
인라인 뷰(Inline View)나 저장된 뷰의 쿼리 블록을 메인 쿼리 블록과 병합하는 과정입니다. 

> [!WARNING]
> **View Merging 실패 사례**
> 뷰 내부에 `GROUP BY`, `DISTINCT`, `ROWNUM` 등이 포함되어 있으면 옵티마이저는 뷰를 병합하지 못하고 별도의 뷰(View) 오퍼레이션으로 묶어버립니다(No Merge). 이로 인해 바깥쪽의 조건절이 안쪽으로 밀고 들어가는 것(Predicate Pushing)이 차단되어 풀 스캔(Full Scan)이 발생할 수 있습니다.

## 2. 조건절 이행(Transitive Predicate)과 조인 순서

`A.deptno = B.deptno` 이고 `A.deptno = 10` 이면, 옵티마이저는 `B.deptno = 10` 이라는 조건을 자동으로 추론(이행)하여 추가합니다. 

> [!CAUTION]
> **조건절 이행의 함정**
> 가끔 옵티마이저는 이 추론된 조건 때문에 전혀 의도하지 않은 테이블을 먼저 읽어버리거나(조인 순서 뒤틀림), 잘못된 인덱스를 선택하는 착각을 합니다. 특히 뷰 병합과 결합될 때 예상치 못한 실행계획 꼬임 현상을 유발합니다. 이럴 때는 조인 순서를 강제하는 `/*+ LEADING(A B) */` 힌트가 유효합니다.

---

## 3. 대용량 데이터 로드 시의 우회 기법

쿼리 변환(Query Transformation)이 항상 좋은 것은 아닙니다. 특히 수천만 건을 집계하거나 로드하는 배치 프로그램에서는 옵티마이저의 과도한 개입이 독이 될 수 있습니다.

### 실무적인 우회(Workaround) 전략
1. **NO_UNNEST / NO_MERGE 활용**: 옵티마이저가 억지로 조인으로 묶으려는 것을 막고, 우리가 의도한 집합 단위로 먼저 데이터를 묶어낸(GROUP BY) 뒤에 조인하도록 강제합니다.
2. **인라인 뷰의 블랙박스화**: 인라인 뷰 내부에 `ROWNUM`을 의도적으로 삽입하면, 옵티마이저의 View Merging을 원천 차단하여 실행계획의 독립성을 보장할 수 있습니다.

```sql
-- View Merging을 방지하는 실무 팁 (ROWNUM 활용)
SELECT A.col1, B.total
  FROM TABLE_A A,
       (SELECT /*+ NO_MERGE */ col1, SUM(col2) as total 
          FROM TABLE_B 
         GROUP BY col1
         -- ROWNUM > 0 을 추가하면 옵티마이저가 절대 뷰를 깨지 못함
        ) B
 WHERE A.col1 = B.col1;
```
