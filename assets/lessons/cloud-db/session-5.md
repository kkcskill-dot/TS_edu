# 5장: AWS 클라우드 환경 이해

클라우드 데이터베이스의 성능과 안정성은 데이터베이스 자체의 설정뿐만 아니라, 그 근간이 되는 클라우드 인프라 아키텍처에 크게 좌우됩니다. DBA가 꼭 알아야 할 AWS의 핵심 인프라 개념을 살펴봅니다.

## 1. VPC (Virtual Private Cloud)와 서브넷

AWS 환경에서 모든 리소스는 논리적으로 격리된 가상 네트워크인 **VPC** 내에 배포됩니다. 온프레미스 네트워크 구성의 클라우드 버전이라 할 수 있습니다.

### 서브넷 (Subnets)과 보안
- **퍼블릭 서브넷 (Public Subnet)**: 인터넷 게이트웨이(IGW)와 연결되어 외부 인터넷망과 통신이 가능한 영역입니다. 주로 웹 서버(ALB 등)가 배치됩니다.
- **프라이빗 서브넷 (Private Subnet)**: 외부 인터넷망과 직접 통신할 수 없는 영역입니다. 데이터 보안이 중요한 **데이터베이스(RDS, Aurora)는 반드시 프라이빗 서브넷에 배치**되어야 합니다.

### 보안 그룹 (Security Group, SG)
- 인스턴스 수준의 가상 방화벽입니다.
- 오라클 리스너(Listener) 접근 제어나 `sqlnet.ora`를 통한 IP 통제를 대신하여, Security Group 인바운드 규칙을 통해 특정 애플리케이션 서버나 Bastion Host의 IP/포트 접근만을 허용합니다.

## 2. 가용 영역 (AZ)과 리전 (Region)

클라우드의 가장 큰 장점 중 하나는 물리적 장애에 대한 회복탄력성(Resilience)입니다.

- **리전 (Region)**: 서울(ap-northeast-2), 버지니아 북부 등 지리적으로 떨어진 독립된 클라우드 데이터 센터 군집입니다.
- **가용 영역 (Availability Zone, AZ)**: 하나의 리전 내에 존재하는 독립적인 데이터 센터들입니다. 각 AZ는 전력, 통신망이 완전히 분리되어 있어 하나의 AZ에 화재가 발생해도 다른 AZ는 정상 작동합니다.
- **DB Multi-AZ 구성**: Aurora는 스토리지 단에서 기본적으로 3개의 AZ에 걸쳐 데이터를 복제하며, 컴퓨팅 인스턴스 역시 여러 AZ에 분산 배치(Primary 1대, Replica 다수)하여 장애 시 즉각적인 페일오버를 수행합니다.

## 3. 인스턴스 타입의 이해

온프레미스 서버를 사이징할 때 CPU Core 수와 Memory를 지정했던 것처럼, AWS에서는 인스턴스 타입을 선택합니다. (예: `db.r6g.4xlarge`)

- **패밀리 (Family)**: 인스턴스의 특성을 나타냅니다. 
  - `t` 타입: 범용, 크레딧 기반 (테스트용)
  - `m` 타입: 범용 (CPU와 메모리 균형)
  - `r` 타입: **메모리 최적화 (DB용으로 가장 널리 쓰임)**. 오라클의 대형 SGA나 MySQL의 버퍼 풀 확보에 유리합니다.
- **프로세서**: `g`가 붙은 모델(예: r6**g**)은 AWS가 자체 설계한 ARM 기반 Graviton 프로세서로, 동일 비용 대비 더 높은 가성비와 성능을 제공합니다.
- **크기 (Size)**: `large`, `xlarge` 등으로 CPU 코어 수와 메모리 양이 결정됩니다.

## 4. 모니터링 생태계 (CloudWatch & SNS)

- **CloudWatch**: AWS 리소스의 각종 지표(CPU, 네트워크 IO, Freeable Memory 등)를 수집하는 모니터링의 핵심 허브입니다.
- 특정 지표가 임계치를 넘으면(예: CPU 90% 초과) CloudWatch Alarm이 발생하고, **SNS (Simple Notification Service)**를 통해 담당 DBA의 이메일이나 슬랙 등으로 알람이 즉시 전송되도록 파이프라인을 구축할 수 있습니다.

> [!IMPORTANT]
> 온프레미스 장비 관리가 시스템 엔지니어(SE)의 몫이었다면, 클라우드 환경에서는 DBA 역시 인스턴스의 타입 변경(Scale-up), 가용 영역의 배치, 보안 그룹 설정 등 인프라스트럭처로서의 코드(IaC) 역량을 넓혀가는 것이 중요합니다.
