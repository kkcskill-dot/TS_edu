# 2장: 스토리지와 컴퓨팅의 분리 (Log is the Database)

전통적인 오라클 DB 아키텍처에서는 트랜잭션을 처리할 때 CPU, 메모리, 그리고 디스크 I/O가 단일 서버(또는 RAC 노드) 내에서 복잡하게 얽혀 있었습니다. Aurora는 **"Log is the Database"**라는 철학을 바탕으로 이 구조를 혁신적으로 분리했습니다.

## 1. 기존 RDBMS의 I/O 병목

오라클이나 표준 MySQL과 같은 전통적인 데이터베이스에서는 하나의 트랜잭션을 커밋하기 위해 다수의 파일 쓰기 작업이 발생합니다.

- **Redo Log / WAL (Write-Ahead Log)** 쓰기
- **Data File (블록/페이지)** 쓰기 (DBWR 플러시)
- **Undo / Rollback Segment** 쓰기
- **Doublewrite Buffer** (MySQL의 경우)

이러한 수많은 I/O는 트랜잭션 양이 많아질수록 I/O 병목을 유발하며, 네트워크 기반 스토리지(EBS 등)를 사용할 때 지연(Latency)의 주된 원인이 됩니다.

## 2. Aurora의 I/O 최적화 (Log-Structured Storage)

Aurora는 컴퓨팅 노드(DB 인스턴스)가 **오직 Redo Log 레코드만** 스토리지 노드로 전송하도록 설계되었습니다. 데이터 페이지(블록) 자체를 네트워크로 전송하거나 디스크에 쓰는 작업을 컴퓨팅 노드에서 제거(Offload)한 것입니다.

### 스토리지 노드의 역할
컴퓨팅 노드로부터 Redo Log를 전달받은 분산 스토리지 노드는 다음 작업들을 비동기적으로 수행합니다.
1. Redo Log를 수신하고 메모리에 캐싱
2. 로그를 기반으로 실제 데이터 페이지(Data Page)를 합성(Materialize)
3. 지속적인 백업을 위해 S3로 데이터를 스트리밍
4. 오래된 버전을 정리(Garbage Collection)

이로 인해 네트워크 트래픽은 기존 대비 1/5 수준으로 감소하며, I/O 대기로 인한 시스템 지연 현상이 획기적으로 개선됩니다.

## 3. 고가용성 (High Availability) 메커니즘

Aurora 스토리지 볼륨은 3개의 가용 영역(AZ)에 걸쳐 총 6개의 복제본(Copy)을 유지합니다. 

- **Quorum 쓰기**: 6개의 복제본 중 4개의 복제본에 쓰기(Write)가 성공하면 트랜잭션이 커밋된 것으로 간주합니다. (장애 내성: 2개의 노드가 동시에 다운되어도 쓰기 가능)
- **Quorum 읽기**: 6개의 복제본 중 3개의 응답을 받으면 유효한 읽기로 처리합니다.
- **자동 복구 (Peer-to-Peer Gossip)**: 스토리지 노드 중 하나에 장애가 발생하면, 다른 노드들과 통신하여 누락된 데이터를 백그라운드에서 자동으로 복구합니다.

> [!NOTE]
> **오라클 DBA를 위한 시사점**
> 오라클 환경에서는 스토리지 장애 대비를 위해 ASM 미러링이나 RAID 구성을 고민해야 했습니다. Aurora에서는 AWS 스토리지 레이어가 이 모든 것을 자동으로 처리하므로, 논리적인 데이터 무결성과 스키마 설계에 더 집중할 수 있습니다.
