# 2과목. SQL 기본 및 활용
## 3장. 관리 구문과 성능 최적화 원리

> [!TIP]
> **들어가며**
> 이 장은 단순한 쿼리 작성을 넘어, 데이터베이스가 데이터를 어떻게 관리하고 쿼리를 어떻게 실행하는지(옵티마이저)를 다룬다. 특히 튜닝의 바탕이 되는 **인덱스와 조인 원리**는 SQLD를 넘어 전문가 과정까지 이어지는 중요한 뼈대다.

---

### 1. DDL, DML, TCL의 이해

데이터베이스를 다루는 언어들은 저마다 파급력과 동작 방식이 다르다.

#### 1.1 DELETE vs TRUNCATE vs DROP (단골 문제)

| 명령어 | 구분 | 대상 | Auto Commit 여부 | 롤백(복구) 여부 | 시스템 부하 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **DELETE** | **DML** | 데이터(행 단위) | X (수동) | **O (가능)** | 큼 (Undo 로그 기록) |
| **TRUNCATE** | **DDL** | 데이터 전체 | **O (자동)** | **X (불가능)** | 매우 작음 (빠름) |
| **DROP** | **DDL** | 테이블 구조 자체 | **O (자동)** | **X (불가능)** | 작음 |

> **주의**: 오라클에서 DDL(`CREATE`, `ALTER`, `DROP`, `TRUNCATE`)은 실행되는 순간 내부적으로 곧바로 `COMMIT`을 수행한다. 그래서 `INSERT` 도중에 DDL을 실행하면 앞서 한 `INSERT`까지 함께 커밋되어 되돌릴 수 없게 된다.

#### 1.2 트랜잭션 (Transaction)의 4가지 특성 (ACID)
1.  **원자성(Atomicity)**: 트랜잭션은 완전히 성공하거나 완전히 실패해야 한다 (All or Nothing).
2.  **일관성(Consistency)**: 트랜잭션 전후로 데이터베이스의 무결성 제약조건이 늘 지켜져야 한다.
3.  **고립성(Isolation)**: 한 트랜잭션이 실행되는 동안 다른 트랜잭션이 끼어들거나 중간 결과를 볼 수 없어야 한다.
4.  **영속성(Durability)**: 성공적으로 커밋된 트랜잭션의 결과는 영구히 남아야 한다.

### 2. DCL (데이터 제어어)

사용자에게 권한을 주거나 거두어들이는 명령어다.

*   **권한 부여**: `GRANT 권한 ON 객체 TO 사용자;`
    *   (예: `GRANT SELECT, INSERT ON EMP TO USER01;`)
*   **권한 회수**: `REVOKE 권한 ON 객체 FROM 사용자;`
    *   (예: `REVOKE DELETE ON EMP FROM USER01;`)
*   **ROLE (역할)**: 여러 권한을 하나로 묶어 둔 바구니다. 사용자마다 권한을 낱낱이 부여하는 대신 '개발자 롤' 같은 묶음을 만들어 한 번에 준다.

### 3. 옵티마이저 (Optimizer)

사용자가 던진 SQL을 가장 빠르고 저렴하게 처리할 **실행 계획(Execution Plan)**을 세워 주는, 데이터베이스의 내비게이션 같은 존재다.

#### 3.1 옵티마이저의 종류
1.  **규칙 기반 옵티마이저 (RBO)**: 미리 정해진 우선순위 규칙에 따라 기계적으로 길을 찾는다. 오래된 방식으로, 인덱스가 있으면 무조건 인덱스를 탄다.
2.  **비용 기반 옵티마이저 (CBO)**: 테이블의 통계 정보(데이터 건수, 인덱스 분포도 등)를 분석해 **비용(Cost)이 가장 적게 드는 길**을 찾는다. 오늘날 대부분의 데이터베이스가 이 방식을 쓴다.

### 4. 인덱스 (Index) 와 스캔 방식

인덱스는 책의 '찾아보기'처럼 데이터를 빠르게 찾도록 돕는 구조로, 주로 **B-Tree (Balanced Tree)**를 쓴다.

#### 4.1 테이블 스캔 방식
*   **Full Table Scan**: 인덱스를 타지 않고 테이블의 모든 블록을 처음부터 끝까지 읽는다. 데이터가 아주 적거나 전체의 대부분(보통 10~15% 이상)을 읽어야 할 때는 오히려 인덱스보다 빠르다. (Multi-block I/O 사용)
*   **Index Range Scan**: 인덱스의 특정 범위를 훑어 데이터의 ROWID를 찾은 뒤 테이블을 찾아가는 방식이다.

#### 4.2 인덱스를 못 타는 경우 (Full Table Scan 유발)
인덱스를 만들어 두어도 아래처럼 쿼리를 짜면 옵티마이저가 인덱스를 쓰지 않는다.
1.  **좌변 가공**: 인덱스 컬럼에 함수를 씌운 경우다. (`WHERE SUBSTR(사번, 1, 2) = '10'`)
2.  **암시적 형변환**: 숫자형 인덱스 컬럼에 문자열을 비교한 경우다. (`WHERE 사번 = '1001'`)
3.  **부정형 비교**: `!=`, `<>`, `NOT IN`을 쓴 경우다. 반대쪽 데이터가 너무 많기 때문이다.
4.  **IS NULL / IS NOT NULL**: 일반적인 B-Tree 인덱스는 NULL을 트리에 저장하지 않으므로 이 조건으로는 인덱스를 탈 수 없다.

### 5. 조인 수행 원리 (조인 메커니즘)

`JOIN`을 쓰면 내부적으로 다음 세 가지 알고리즘 가운데 하나로 처리된다.

#### 5.1 Nested Loop Join (NL 조인)
*   **원리**: 이중 반복문과 같다. 선행 테이블(Driving Table)에서 조건에 맞는 행을 하나씩 꺼내, 후행 테이블(Driven Table)에서 조인 조건에 맞는 데이터를 찾는다.
*   **특징**
    *   랜덤 I/O가 많이 발생해 대용량 조인에서는 느리다.
    *   후행 테이블의 조인 컬럼에는 반드시 인덱스가 있어야 한다. 인덱스가 없으면 매번 Full Scan을 하게 되어 부하가 크다.
    *   좁은 범위를 처리하는 온라인 트랜잭션(OLTP)에 유리하다.

#### 5.2 Sort Merge Join (정렬 병합 조인)
*   **원리**: 두 테이블을 각각 조인 컬럼 기준으로 미리 정렬(Sort)한 뒤 나란히 병합(Merge)한다.
*   **특징**
    *   인덱스가 없어도 쓸 수 있다.
    *   등가(=) 조건이 아닌 크기 비교(`<`, `>`, `BETWEEN`) 조인에서도 쓸 수 있다.
    *   다만 정렬 작업이 메모리를 많이 써서 대용량에서는 부담이 크다.

#### 5.3 Hash Join (해시 조인)
*   **원리**: 크기가 작은 선행 테이블을 읽어 해시 맵(Hash Map)을 만들고, 후행 테이블을 읽으면서 해시 함수로 짝을 찾는다.
*   **특징**
    *   대용량 데이터 조인에서 빠르다. NL 조인의 랜덤 I/O 문제를 피한다.
    *   오직 등가 조인(Equal Join, `=`)에서만 쓸 수 있다.
    *   데이터 웨어하우스(DW)의 야간 배치 작업 등에 주로 쓰인다.
