# 2과목. SQL 기본 및 활용
## 3장. 관리 구문과 성능 최적화 원리

> [!TIP]
> **DBA와 튜너의 영역**
> 이 장은 단순한 쿼리 작성을 넘어, 데이터베이스가 데이터를 어떻게 관리하고 쿼리를 어떻게 실행하는지(옵티마이저)를 다룹니다. 특히 튜닝의 기초가 되는 **인덱스와 조인 원리**는 SQLD를 넘어 SQLP(전문가)까지 이어지는 가장 중요한 뼈대입니다.

---

### 1. DDL, DML, TCL의 이해

데이터베이스를 조작하는 언어들은 각각 그 파급력과 동작 방식이 다릅니다.

#### 1.1 DELETE vs TRUNCATE vs DROP (단골 문제)

| 명령어 | 구분 | 대상 | Auto Commit 여부 | 롤백(복구) 여부 | 시스템 부하 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **DELETE** | **DML** | 데이터(행 단위) | X (수동) | **O (가능)** | 큼 (Undo 로그 기록) |
| **TRUNCATE** | **DDL** | 데이터 전체 | **O (자동)** | **X (불가능)** | 매우 작음 (빠름) |
| **DROP** | **DDL** | 테이블 구조 자체 | **O (자동)** | **X (불가능)** | 작음 |

> 🚨 **주의**: 오라클에서 DDL(`CREATE`, `ALTER`, `DROP`, `TRUNCATE`)은 실행되는 순간 내부적으로 즉시 `COMMIT`을 날려버립니다. 만약 DML(`INSERT`)을 하다가 DDL을 실행하면, 이전까지 했던 `INSERT`도 함께 커밋되어 버립니다!

#### 1.2 트랜잭션 (Transaction)의 4가지 특성 (ACID)
1.  **원자성(Atomicity)**: 트랜잭션은 완전히 성공하거나 완전히 실패해야 함 (All or Nothing).
2.  **일관성(Consistency)**: 트랜잭션 전후로 데이터베이스의 무결성 제약조건은 항상 유지되어야 함.
3.  **고립성(Isolation)**: 하나의 트랜잭션이 실행되는 동안 다른 트랜잭션이 끼어들거나 결과를 볼 수 없음.
4.  **영속성(Durability)**: 성공적으로 완료(Commit)된 트랜잭션의 결과는 영구적으로 반영되어야 함.

### 2. DCL (데이터 제어어)

사용자에게 권한을 주거나 뺏는 명령어입니다.

*   **권한 부여**: `GRANT 권한 ON 객체 TO 사용자;`
    *   (예: `GRANT SELECT, INSERT ON EMP TO USER01;`)
*   **권한 회수**: `REVOKE 권한 ON 객체 FROM 사용자;`
    *   (예: `REVOKE DELETE ON EMP FROM USER01;`)
*   **ROLE (역할)**: 수많은 권한들을 묶어놓은 바구니입니다. 사용자마다 일일이 수십 개의 권한을 주는 대신, '개발자 롤'을 만들어 롤을 한 번에 부여합니다.

---

### 3. 옵티마이저 (Optimizer) 🏆 (심화 영역)

사용자가 던진 SQL을 어떻게 실행할지 가장 빠르고 저렴한 **실행 계획(Execution Plan)**을 세워주는 데이터베이스의 '내비게이션'입니다.

#### 3.1 옵티마이저의 종류
1.  **규칙 기반 옵티마이저 (RBO)**: 미리 정해진 15개의 우선순위 규칙에 따라 기계적으로 길을 찾습니다. (오래된 방식. 인덱스가 있으면 무조건 인덱스를 탐)
2.  **비용 기반 옵티마이저 (CBO)**: 테이블의 통계 정보(데이터 건수, 인덱스 분포도 등)를 분석하여 **가장 비용(Cost)이 적게 드는 길**을 찾습니다. (현재 대부분의 DB가 채택)

### 4. 인덱스 (Index) 와 스캔 방식

데이터를 빠르게 찾기 위해 책의 '색인(찾아보기)'을 만드는 것과 같습니다. 주로 **B-Tree (Balanced Tree)** 구조를 사용합니다.

#### 4.1 테이블 스캔 방식
*   **Full Table Scan**: 인덱스를 타지 않고 테이블의 모든 블록을 처음부터 끝까지 다 읽습니다. 데이터가 아주 적거나, 전체 데이터의 대다수(보통 10~15% 이상)를 읽을 때는 인덱스보다 오히려 빠릅니다. (Multi-block I/O 사용)
*   **Index Range Scan**: 인덱스의 특정 범위를 스캔하여 해당 데이터의 ROWID를 찾은 뒤, 테이블을 찾아가는 방식입니다.

#### 4.2 인덱스를 못 타는 경우 (Full Table Scan 유발)
아무리 인덱스를 만들어 놔도 아래처럼 쿼리를 짜면 옵티마이저는 인덱스를 버립니다.
1.  **좌변 가공**: 인덱스 컬럼에 함수를 씌운 경우 (`WHERE SUBSTR(사번, 1, 2) = '10'`)
2.  **암시적 형변환**: 숫자형 인덱스 컬럼에 문자열을 비교한 경우 (`WHERE 사번 = '1001'`)
3.  **부정형 비교**: `!=`, `<>`, `NOT IN` 연산자를 사용한 경우. (반대쪽 데이터가 너무 방대하기 때문)
4.  **IS NULL / IS NOT NULL**: 일반적인 B-Tree 인덱스는 NULL 값을 인덱스 트리에 저장하지 않으므로 검색할 수 없습니다.

### 5. 조인 수행 원리 (조인 메커니즘) 🏆 (시험 무조건 출제)

SQL에서 `JOIN`을 썼을 때 내부적으로 돌아가는 3가지 핵심 알고리즘입니다.

#### 5.1 Nested Loop Join (NL 조인)
*   **원리**: 이중 For 문과 같습니다. 선행 테이블(Driving Table)의 조건을 만족하는 행을 하나씩 빼서, 후행 테이블(Driven Table)에 가서 조인 조건에 맞는 데이터를 찾습니다.
*   **특징**:
    *   **랜덤 I/O**가 대량으로 발생하여 대용량 데이터 조인 시 매우 느립니다.
    *   반드시 **후행 테이블의 조인 컬럼에 인덱스**가 있어야 합니다. (인덱스가 없으면 매번 Full Scan을 하므로 시스템이 마비됩니다.)
    *   온라인 트랜잭션(OLTP) 등 좁은 범위의 처리에 유리합니다.

#### 5.2 Sort Merge Join (정렬 병합 조인)
*   **원리**: 두 테이블을 각각 조인 컬럼 기준으로 미리 정렬(Sort)한 다음, 쫙 병합(Merge)합니다.
*   **특징**:
    *   인덱스가 없어도 사용할 수 있습니다.
    *   동등(=) 조건이 아닌 크기 비교(`<`, `>`, `BETWEEN`) 조인에서도 사용할 수 있습니다.
    *   하지만 정렬 작업(Sort) 자체가 메모리를 엄청나게 잡아먹어 대용량에서는 무리가 갑니다.

#### 5.3 Hash Join (해시 조인)
*   **원리**: 크기가 작은 선행 테이블을 읽어 해시 메모리에 해시 맵(Hash Map)을 만들고, 후행 테이블을 읽으면서 해시 함수를 통해 짝을 찾습니다.
*   **특징**:
    *   **대용량 데이터 조인에 압도적으로 빠릅니다!** (NL 조인의 랜덤 I/O 극복)
    *   오직 **동등 조인(Equal Join, `=`)에서만** 쓸 수 있습니다.
    *   데이터 웨어하우스(DW) 등 야간 배치 작업에 주로 쓰입니다.
