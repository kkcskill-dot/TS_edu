# 1과목. 데이터 모델링의 이해
## 2장. 데이터 모델과 성능 (성능 데이터 모델링)

> [!TIP]
> **성능 데이터 모델링이란?**
> 데이터베이스의 성능은 하드웨어 장비(CPU, Memory)를 늘리거나 쿼리를 튜닝하는 것만으로는 한계가 있습니다. 가장 근본적인 성능 병목은 **잘못 설계된 데이터 모델**에서 발생합니다. 2장에서는 정규화를 통한 성능 향상과 그 반대인 반정규화, 그리고 대용량 데이터 처리 기법을 다룹니다.

---

### 1. 성능 데이터 모델링의 개요

#### 1.1 성능 데이터 모델링의 수행 시점
*   성능 데이터 모델링은 **데이터 모델링 전반(분석/설계 단계)**에 걸쳐 수행되어야 합니다.
*   사전에 설계 단계에서 성능을 고려하지 않으면, 프로젝트 후반부(테스트나 운영 단계)에서 성능 문제가 터졌을 때 데이터 모델 구조 자체를 뜯어고쳐야 하므로 엄청난 재작업 비용이 발생합니다.

#### 1.2 성능 데이터 모델링 수행 절차
1.  정규화를 정확하게 수행하여 이상 현상(Anomaly)을 제거합니다.
2.  데이터베이스 용량 산정 및 트랜잭션의 유형을 파악합니다.
3.  용량과 트랜잭션 유형을 바탕으로 반정규화를 고려합니다.
4.  이력 모델의 조정, PK/FK 조정, 슈퍼/서브타입 조정을 수행합니다.
5.  성능 관점에서 데이터 모델을 검증합니다.

---

### 2. 정규화 (Normalization) 🏆 (시험 무조건 출제)

#### 2.1 정규화의 목적
데이터의 **중복을 최소화**하고, 데이터가 삽입/수정/삭제될 때 발생하는 **이상 현상(Anomaly)**을 방지하기 위해 릴레이션(테이블)을 분해하는 과정입니다. 
정규화는 데이터의 '입력/수정/삭제' 성능을 향상시키지만, '조회(SELECT)' 시에는 조인(JOIN)이 발생하여 성능이 저하될 수도 있습니다.

#### 2.2 제1정규형 (1NF) : 원자성 확보
**"모든 속성은 반드시 하나의 원자값(Atomic Value)만 가져야 한다."**
하나의 컬럼에 여러 개의 값이 들어가 있거나, 비슷한 컬럼(아이템1, 아이템2, 아이템3)이 반복되는 경우 분리합니다.

**[비정규화 테이블: 취미가 2개]**
| 회원ID(PK) | 이름 | 취미 |
| :--- | :--- | :--- |
| U001 | 김철수 | 독서, 등산 |
| U002 | 이영희 | 수영 |

**[1차 정규화 완료]** (1:M 관계로 분리)
| 회원ID(FK) | 취미 |
| :--- | :--- |
| U001 | 독서 |
| U001 | 등산 |
| U002 | 수영 |

#### 2.3 제2정규형 (2NF) : 부분 함수 종속성 제거
**"주식별자가 2개 이상의 복합키일 때, 일반 속성은 주식별자 전체에 종속되어야 한다."**
주식별자의 '일부'에만 종속되는 속성이 있다면 별도의 테이블로 분리해야 합니다.

**[1차 정규형: 주문상품 테이블]**
*주식별자: (주문번호 + 상품코드)*
| 주문번호(PK) | 상품코드(PK) | 주문수량 | 상품명 |
| :--- | :--- | :--- | :--- |
| O001 | P01 | 2 | 노트북 |
| O001 | P02 | 1 | 마우스 |
| O002 | P01 | 5 | 노트북 |

> 🚨 문제점: `상품명`은 주식별자 전체(주문번호+상품코드)에 종속된 것이 아니라, `상품코드` 하나에만 종속됩니다. (부분 종속)

**[2차 정규화 완료]**
* **주문상세 테이블**: 주문번호, 상품코드, 주문수량
* **상품 테이블**: 상품코드, 상품명 (분리됨)

#### 2.4 제3정규형 (3NF) : 이행적 함수 종속 제거
**"일반 속성끼리 서로 종속되지 않아야 한다."**
주식별자가 아닌 일반 속성 B가 일반 속성 A에 종속되는 현상(X->A 이고 A->B 일 때 X->B)을 제거합니다.

**[2차 정규형: 부서정보 포함 테이블]**
*주식별자: 사번*
| 사번(PK) | 이름 | 부서코드 | 부서명 |
| :--- | :--- | :--- | :--- |
| 1001 | 김철수 | D01 | 개발팀 |
| 1002 | 이영희 | D01 | 개발팀 |

> 🚨 문제점: `부서명`은 PK인 `사번`에 종속된 것이 아니라, 일반 속성인 `부서코드`에 종속되어 있습니다.

**[3차 정규화 완료]**
* **사원 테이블**: 사번, 이름, 부서코드(FK)
* **부서 테이블**: 부서코드(PK), 부서명 (분리됨)

#### 2.5 보이스-코드 정규형 (BCNF)
**"릴레이션의 모든 결정자(Determinant)는 후보키여야 한다."**
제3정규형을 만족하더라도, 후보키가 여러 개이고 서로 중첩되는 특수한 경우에는 이상 현상이 남을 수 있습니다. BCNF는 3정규형을 더 엄격하게 한 형태로 **'3.5 정규형'**이라고도 부릅니다.

*   **결정자(Determinant)**: 다른 속성의 값을 결정하는 속성. (X → Y 에서 X)
*   후보키가 **아닌** 결정자가 존재하면 BCNF 위배입니다.

**[예제: 학생-과목-교수]** (업무 규칙: 한 교수는 오직 한 과목만 강의한다 → `교수 → 과목`)
| 학생(PK) | 과목(PK) | 교수 |
| :--- | :--- | :--- |
| 김철수 | 데이터베이스 | 이교수 |
| 이영희 | 데이터베이스 | 이교수 |
| 김철수 | 네트워크 | 박교수 |

> 🚨 문제점: 후보키는 `(학생, 과목)`과 `(학생, 교수)`입니다. 그런데 `교수 → 과목` 종속에서 결정자인 `교수`는 후보키가 아닙니다. 이 테이블은 **제3정규형은 만족하지만 BCNF는 위배**합니다.

**[BCNF 분해 완료]**
* **수강 테이블**: 학생, 교수
* **강의 테이블**: 교수(PK), 과목

> 💡 SQLD에서는 1~3정규형이 핵심 출제 범위이며, BCNF는 '결정자 = 후보키'라는 정의와 3정규형과의 차이를 묻는 수준으로 출제됩니다.

### 3. 반정규화 (De-normalization)

#### 3.1 반정규화란?
정규화를 마친 모델이 **조회(SELECT) 성능**이 심각하게 저하될 것으로 예상될 때, 성능 향상을 위해 **데이터의 중복을 허용**하여 데이터 모델을 의도적으로 망가뜨리는(통합하는) 기법입니다.
데이터 무결성이 깨질 위험이 크므로 신중하게 적용해야 합니다.

#### 3.2 반정규화 기법
1.  **테이블 반정규화**
    *   **테이블 병합**: 1:1 관계, 1:M 관계 병합, 슈퍼/서브 타입 병합
    *   **테이블 분할**: 수직 분할(컬럼 단위 분리), 수평 분할(로우 단위 분리 - *추후 파티셔닝과 유사*)
    *   **테이블 추가**: 중복 테이블 추가, 통계 테이블 추가, 이력 테이블 추가, 부분 테이블 추가
2.  **컬럼 반정규화** (가장 빈번함)
    *   **중복 컬럼 추가**: 조인을 줄이기 위해 부모 테이블의 컬럼을 자식 테이블에 중복 저장.
    *   **파생 컬럼 추가**: 계산 로직(SUM, AVG 등)을 미리 수행하여 그 결과값을 컬럼에 저장. (예: 총 잔액, 총 주문금액)
    *   **이력 테이블 컬럼 추가**: 최신 값을 찾기 위해 이력 테이블을 모두 스캔하지 않도록, 마스터 테이블에 '최신여부' 컬럼을 둠.
3.  **관계 반정규화**
    *   **중복 관계 추가**: 여러 경로를 거쳐 조인해야 하는 먼 거리의 엔터티를 다이렉트로 연결하는 관계를 추가. (데이터 무결성에 영향을 주지 않는 유일한 반정규화 기법)

### 4. 대용량 데이터 성능 저하와 파티셔닝

#### 4.1 대용량 데이터의 문제점
테이블에 수천만, 수억 건의 데이터가 쌓이면 인덱스 트리(B-Tree)의 깊이가 깊어지고 크기가 거대해져, 인덱스를 타더라도 검색 성능이 저하됩니다.

#### 4.2 파티셔닝 (Partitioning)
물리적인 데이터 파일을 분할하여 성능을 향상시키는 기법입니다. **논리적으로는 1개의 테이블이지만 물리적으로는 여러 개의 테이블스페이스에 분산 저장**됩니다.

| 종류 | 설명 | 사용 예시 |
| :--- | :--- | :--- |
| **RANGE 파티셔닝** | 가장 많이 쓰임. 연속적인 값(날짜, 숫자)의 범위로 분할. | 월별 파티션 (2026-01, 2026-02...) |
| **LIST 파티셔닝** | 특정한 값(코드)을 기준으로 분할. | 지점별 파티션 (서울, 부산, 대구) |
| **HASH 파티셔닝** | 해시 함수 결과에 따라 시스템이 임의로 균등하게 분할. 관리가 어려움. | 데이터가 특정 범위나 값에 치우치지 않을 때 |

### 5. 분산 데이터베이스

네트워크를 통해 여러 곳에 흩어져 있는 데이터베이스를 하나의 논리적인 데이터베이스처럼 사용할 수 있게 하는 기술입니다.

#### 5.1 분산 데이터베이스의 투명성 (Transparency)
사용자는 데이터가 어디에, 어떻게 분산되어 있는지 몰라도 됩니다.
*   **분할 투명성**: 하나의 릴레이션이 분할되어 있는지 알 필요 없음.
*   **위치 투명성**: 데이터의 물리적 위치를 알 필요 없음.
*   **지역사상 투명성**: 지역DBMS와 무관하게 애플리케이션 작성 가능.
*   **중복 투명성**: 데이터가 여러 곳에 중복 복제되어 있는지 알 필요 없음.
*   **장애 투명성**: 한 곳에 장애가 발생해도 시스템은 정상 작동함.
*   **병행 투명성**: 여러 트랜잭션이 동시에 실행되어도 데이터 일관성 유지.

#### 5.2 분산 데이터베이스 적용 기법
*   **테이블 위치 분산**: 테이블 구조는 동일하지만, A지점 테이블은 A서버에, B지점 테이블은 B서버에 위치.
*   **테이블 분할 분산**: 한 테이블을 나누어 분산 (수평 분할 / 수직 분할).
*   **테이블 복제(Replication) 분산**: **가장 많이 쓰임.** 마스터 DB의 데이터를 지사 DB로 지속적으로 복제하여, 각 지사에서 빠른 로컬 조인이 가능하게 함. 조회(Read) 성능 극대화에 탁월.
