# 1과목. 데이터 모델링의 이해
## 2장. 데이터 모델과 성능 (성능 데이터 모델링)

> [!TIP]
> **성능 데이터 모델링이란?**
> 데이터베이스의 성능은 장비(CPU, 메모리)를 늘리거나 쿼리를 손보는 것만으로는 한계가 있다. 가장 깊은 병목은 대개 **잘못 설계된 데이터 모델**에서 비롯된다. 이 장에서는 정규화로 성능을 다지는 방법과 그 반대편에 있는 반정규화, 그리고 대용량 데이터를 다루는 기법을 살펴본다.

---

### 1. 성능 데이터 모델링의 개요

#### 1.1 성능 데이터 모델링의 수행 시점
성능 데이터 모델링은 분석·설계 단계를 포함한 **모델링 전반**에 걸쳐 이루어져야 한다. 설계 단계에서 성능을 미리 고려하지 않으면, 뒤늦게 테스트나 운영에서 문제가 터졌을 때 모델 구조 자체를 뜯어고쳐야 하고 그만큼 재작업 비용이 커진다.

#### 1.2 성능 데이터 모델링 수행 절차
1.  정규화를 정확히 수행해 이상 현상(Anomaly)을 없앤다.
2.  데이터베이스 용량을 산정하고 트랜잭션의 유형을 파악한다.
3.  용량과 트랜잭션 유형을 바탕으로 반정규화를 검토한다.
4.  이력 모델, PK/FK, 슈퍼·서브타입을 조정한다.
5.  성능 관점에서 데이터 모델을 최종 검증한다.

---

### 2. 정규화 (Normalization)

정규화는 시험에 거의 빠짐없이 나오는 핵심 주제다.

#### 2.1 정규화의 목적
정규화란 데이터의 **중복을 줄이고**, 삽입·수정·삭제 과정에서 생기는 **이상 현상(Anomaly)**을 막기 위해 릴레이션(테이블)을 나누는 과정이다. 정규화를 하면 입력·수정·삭제 성능은 좋아지지만, 테이블이 나뉜 만큼 조회할 때 조인이 늘어 성능이 떨어질 수도 있다.

#### 2.2 제1정규형 (1NF) : 원자성 확보
**"모든 속성은 반드시 하나의 원자값(Atomic Value)만 가져야 한다."**
한 컬럼에 여러 값이 들어 있거나 비슷한 컬럼(아이템1, 아이템2, 아이템3)이 반복되면 이를 나눈다.

**[비정규화 테이블: 취미가 2개]**
| 회원ID(PK) | 이름 | 취미 |
| :--- | :--- | :--- |
| U001 | 김철수 | 독서, 등산 |
| U002 | 이영희 | 수영 |

**[1차 정규화 완료]** (1:M 관계로 분리)
| 회원ID(FK) | 취미 |
| :--- | :--- |
| U001 | 독서 |
| U001 | 등산 |
| U002 | 수영 |

#### 2.3 제2정규형 (2NF) : 부분 함수 종속성 제거
**"주식별자가 두 개 이상의 복합키일 때, 일반 속성은 주식별자 전체에 종속되어야 한다."**
주식별자의 '일부'에만 종속되는 속성이 있다면 별도의 테이블로 떼어 낸다.

**[1차 정규형: 주문상품 테이블]**
*주식별자: (주문번호 + 상품코드)*
| 주문번호(PK) | 상품코드(PK) | 주문수량 | 상품명 |
| :--- | :--- | :--- | :--- |
| O001 | P01 | 2 | 노트북 |
| O001 | P02 | 1 | 마우스 |
| O002 | P01 | 5 | 노트북 |

> **짚어 볼 점**: `상품명`은 주식별자 전체(주문번호+상품코드)가 아니라 `상품코드` 하나에만 종속된다. 이것이 부분 종속이다.

**[2차 정규화 완료]**
* **주문상세 테이블**: 주문번호, 상품코드, 주문수량
* **상품 테이블**: 상품코드, 상품명 (분리됨)

#### 2.4 제3정규형 (3NF) : 이행적 함수 종속 제거
**"일반 속성끼리 서로 종속되지 않아야 한다."**
주식별자가 아닌 일반 속성 B가 또 다른 일반 속성 A에 종속되는 현상(X→A 이고 A→B 이면 X→B)을 없앤다.

**[2차 정규형: 부서정보 포함 테이블]**
*주식별자: 사번*
| 사번(PK) | 이름 | 부서코드 | 부서명 |
| :--- | :--- | :--- | :--- |
| 1001 | 김철수 | D01 | 개발팀 |
| 1002 | 이영희 | D01 | 개발팀 |

> **짚어 볼 점**: `부서명`은 PK인 `사번`이 아니라 일반 속성인 `부서코드`에 종속되어 있다.

**[3차 정규화 완료]**
* **사원 테이블**: 사번, 이름, 부서코드(FK)
* **부서 테이블**: 부서코드(PK), 부서명 (분리됨)

#### 2.5 보이스-코드 정규형 (BCNF)
**"릴레이션의 모든 결정자(Determinant)는 후보키여야 한다."**
제3정규형을 만족하더라도, 후보키가 여러 개이고 서로 겹치는 특수한 경우에는 이상 현상이 남을 수 있다. BCNF는 3정규형을 한층 더 엄격하게 다진 것으로, **'3.5 정규형'**이라고도 부른다.

*   **결정자(Determinant)**: 다른 속성의 값을 결정하는 속성이다. (X → Y 에서 X)
*   후보키가 **아닌** 결정자가 존재하면 BCNF에 어긋난다.

**[예제: 학생-과목-교수]** (업무 규칙: 한 교수는 오직 한 과목만 강의한다 → `교수 → 과목`)
| 학생(PK) | 과목(PK) | 교수 |
| :--- | :--- | :--- |
| 김철수 | 데이터베이스 | 이교수 |
| 이영희 | 데이터베이스 | 이교수 |
| 김철수 | 네트워크 | 박교수 |

> **짚어 볼 점**: 후보키는 `(학생, 과목)`과 `(학생, 교수)`다. 그런데 `교수 → 과목` 종속에서 결정자인 `교수`는 후보키가 아니다. 이 테이블은 제3정규형은 만족하지만 BCNF는 위배한다.

**[BCNF 분해 완료]**
* **수강 테이블**: 학생, 교수
* **강의 테이블**: 교수(PK), 과목

> 💡 SQLD에서는 1~3정규형이 핵심 출제 범위이고, BCNF는 '결정자 = 후보키'라는 정의와 3정규형과의 차이를 묻는 정도로 나온다.

### 3. 반정규화 (De-normalization)

#### 3.1 반정규화란?
정규화를 마친 모델에서 **조회(SELECT) 성능**이 크게 떨어질 것으로 예상될 때, 성능을 위해 **데이터 중복을 일부러 허용**해 모델을 통합하는 기법이다. 무결성이 깨질 위험이 있으므로 반드시 신중하게 적용한다.

#### 3.2 반정규화 기법
1.  **테이블 반정규화**
    *   **테이블 병합**: 1:1 관계, 1:M 관계, 슈퍼·서브타입을 하나로 합친다.
    *   **테이블 분할**: 컬럼 단위의 수직 분할, 로우 단위의 수평 분할로 나눈다. (수평 분할은 파티셔닝과 비슷하다.)
    *   **테이블 추가**: 중복·통계·이력·부분 테이블을 새로 둔다.
2.  **컬럼 반정규화** (가장 흔하다)
    *   **중복 컬럼 추가**: 조인을 줄이려고 부모 테이블의 컬럼을 자식 테이블에 함께 저장한다.
    *   **파생 컬럼 추가**: SUM·AVG 같은 계산을 미리 해 그 결과를 컬럼에 담아 둔다. (예: 총 잔액, 총 주문금액)
    *   **이력 테이블 컬럼 추가**: 이력 전체를 훑지 않고도 최신 값을 찾도록, 마스터 테이블에 '최신여부' 컬럼을 둔다.
3.  **관계 반정규화**
    *   **중복 관계 추가**: 여러 단계를 거쳐 조인해야 하는 먼 엔터티를 곧바로 잇는 관계를 더한다. 무결성에 영향을 주지 않는 유일한 반정규화 기법이다.

### 4. 대용량 데이터 성능 저하와 파티셔닝

#### 4.1 대용량 데이터의 문제점
한 테이블에 수천만, 수억 건이 쌓이면 인덱스 트리(B-Tree)가 깊고 커져서, 인덱스를 타더라도 검색 성능이 떨어진다.

#### 4.2 파티셔닝 (Partitioning)
파티셔닝은 물리적인 데이터 파일을 나누어 성능을 끌어올리는 기법이다. **논리적으로는 하나의 테이블이지만, 물리적으로는 여러 테이블스페이스에 나뉘어 저장**된다.

| 종류 | 설명 | 사용 예시 |
| :--- | :--- | :--- |
| **RANGE 파티셔닝** | 가장 많이 쓴다. 날짜·숫자처럼 연속된 값의 범위로 나눈다. | 월별 파티션 (2026-01, 2026-02 …) |
| **LIST 파티셔닝** | 특정한 값(코드)을 기준으로 나눈다. | 지점별 파티션 (서울, 부산, 대구) |
| **HASH 파티셔닝** | 해시 함수로 시스템이 균등하게 나눈다. 관리가 까다롭다. | 데이터가 특정 범위나 값에 치우치지 않을 때 |

### 5. 분산 데이터베이스

분산 데이터베이스는 네트워크로 여러 곳에 흩어진 데이터베이스를 하나의 논리적 데이터베이스처럼 쓰게 해 주는 기술이다.

#### 5.1 분산 데이터베이스의 투명성 (Transparency)
사용자는 데이터가 어디에, 어떻게 흩어져 있는지 몰라도 된다. 이를 투명성이라 하며, 다음과 같이 나뉜다.

*   **분할 투명성**: 하나의 릴레이션이 나뉘어 있는지 몰라도 된다.
*   **위치 투명성**: 데이터의 물리적 위치를 몰라도 된다.
*   **지역사상 투명성**: 지역 DBMS와 무관하게 애플리케이션을 작성할 수 있다.
*   **중복 투명성**: 데이터가 여러 곳에 복제되어 있는지 몰라도 된다.
*   **장애 투명성**: 한 곳에 장애가 생겨도 시스템은 정상 동작한다.
*   **병행 투명성**: 여러 트랜잭션이 동시에 실행되어도 데이터 일관성이 유지된다.

#### 5.2 분산 데이터베이스 적용 기법
*   **테이블 위치 분산**: 구조는 같지만 A지점 테이블은 A서버에, B지점 테이블은 B서버에 둔다.
*   **테이블 분할 분산**: 한 테이블을 수평 또는 수직으로 나누어 분산한다.
*   **테이블 복제(Replication) 분산**: 가장 많이 쓰는 방식이다. 마스터 DB의 데이터를 지사 DB로 꾸준히 복제해, 각 지사에서 빠른 로컬 조인이 가능하게 한다. 조회 성능을 끌어올리는 데 특히 효과적이다.
