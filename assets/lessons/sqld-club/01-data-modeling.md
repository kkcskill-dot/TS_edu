# 1과목. 데이터 모델링의 이해
## 1장. 데이터 모델링의 이해

> [!TIP]
> **개발자를 위한 가이드**
> 코드를 짜기 전에 아키텍처를 고민하듯, DB를 구축하기 전에는 데이터 모델링이 필수입니다. 
> 시스템의 뼈대를 잡는 과정이며, 이곳에서 잘못 꼬이면 훗날 수천 줄의 복잡한 쿼리로 수습해야 하는 대참사가 일어납니다.

---

### 1. 데이터 모델의 이해

#### 모델링이란?
*   다양한 현상을 **추상화**, **단순화**하여 일정한 표기법에 의해 **명확화**하여 표현하는 것입니다.
*   **특징**: 추상화(일정한 형식), 단순화(제한된 표기법), 명확화(애매모호함 제거)
*   **3가지 관점**: 데이터 관점(What), 프로세스 관점(How), 데이터와 프로세스의 상관 관점(Interaction)

#### 데이터 모델링의 3단계 🏆 (시험 단골 출제)
1.  **개념적 데이터 모델링**: 업무 중심적, 포괄적인 수준의 모델링 (전사적 데이터 모델링, EA 수립). 추상화 수준이 가장 높습니다.
2.  **논리적 데이터 모델링**: 테이블, 키, 속성, 관계 등을 도출하며, 재사용성이 높고 **정규화**를 수행하는 단계입니다. 특정 DB 벤더에 종속되지 않습니다.
3.  **물리적 데이터 모델링**: 실제 DB를 구축하기 위해 하드웨어 성능, 디스크 구조 등을 고려하여 물리적 스키마를 설계하는 가장 구체적인 단계입니다.

#### 데이터 독립성 (3단계 스키마 구조)
*   **외부 스키마 (External Schema)**: 사용자, 응용 프로그래머 관점의 요구사항. (사용자가 보는 뷰)
*   **개념 스키마 (Conceptual Schema)**: 조직 전체 관점의 통합적 표현. (DB에 저장되는 데이터와 그 관계)
*   **내부 스키마 (Internal Schema)**: 물리적으로 저장된 형식. 개발자 관점.
*   데이터 독립성은 **논리적 독립성**(개념 스키마가 변경되어도 외부 스키마에 영향 없음)과 **물리적 독립성**(내부 스키마가 변경되어도 외부/개념 스키마에 영향 없음)으로 나뉩니다.

### 2. 엔터티 (Entity)

업무에 필요한 정보를 저장하고 관리하기 위한 집합적인 객체입니다. (인스턴스의 집합)

#### 엔터티의 특징
*   업무에서 반드시 필요하고 관리해야 하는 정보여야 합니다.
*   유일한 식별자에 의해 식별이 가능해야 합니다.
*   **2개 이상의 인스턴스**를 포함해야 합니다.
*   반드시 **속성**을 가져야 합니다.
*   다른 엔터티와 최소 1개 이상의 **관계**가 있어야 합니다. (통계성, 코드성 엔터티 등 예외 있음)

#### 발생 시점에 따른 분류 🏆
1.  **기본/키 (Fundamental) 엔터티**: 그 업무에 원래 존재하는 정보로, 독립적으로 생성되며 다른 엔터티의 부모 역할을 합니다. (예: 사원, 부서, 고객, 상품)
2.  **중심 (Main) 엔터티**: 기본 엔터티로부터 발생되며 그 업무에서 중심적인 역할을 합니다. (예: 계약, 사고, 주문)
3.  **행위 (Active) 엔터티**: 두 개 이상의 부모 엔터티로부터 발생되며, 자주 내용이 바뀌고 데이터 양이 가장 많습니다. (예: 주문목록, 사원변경이력)

---

### 3. 속성 (Attribute)

사물의 특징이나 본질적인 성질로, 인스턴스에 대해 의미상 더 이상 분리되지 않는 최소의 데이터 단위입니다.

#### 속성의 특징
*   해당 업무에서 필요하고 관리해야 하는 정보여야 합니다.
*   모든 속성은 정해진 주식별자에 함수적으로 종속되어야 합니다.
*   하나의 속성은 **오직 한 개의 값**만을 가집니다. (다중값은 별도의 엔터티로 분리해야 함)

#### 속성의 분류
1.  **기본 속성 (Basic)**: 원래 업무로부터 유래된 가장 일반적인 속성.
2.  **설계 속성 (Designed)**: 데이터 모델링을 위해 업무를 규칙화하려고 새로 만들어진 속성. (예: 상품코드, 지점코드)
3.  **파생 속성 (Derived)**: 다른 속성들로부터 계산이나 변형되어 도출된 속성. 가급적 적게 정의해야 합니다. (예: 합계, 평균)

#### 도메인 (Domain)
각 속성이 가질 수 있는 값의 범위나 데이터 타입을 의미합니다. (예: 학점은 0.0~4.5 사이의 실수, 학생 이름은 10자리 이내 문자열 등)

---

### 4. 관계 (Relationship)

엔터티의 인스턴스 간 논리적인 연관성을 의미합니다.

#### 관계의 표기법 (ERD)
*   **관계명 (Relationship Name)**: 엔터티가 관계에 참여하는 형태 (예: 포함한다, 소속된다)
*   **관계차수 (Cardinality)**: 1:1, 1:M, M:N
*   **관계선택사양 (Optionality)**: 필수참여 (Mandatory), 선택참여 (Optional)

---

### 5. 식별자 (Identifier)

엔터티 내에서 각 인스턴스를 유일하게 구분할 수 있는 속성을 말합니다.

#### 주식별자 (Primary Key) 도출 기준 4원칙 🏆 (시험 단골)
1.  **유일성**: 엔터티 내의 모든 인스턴스들을 유일하게 구분해야 합니다.
2.  **최소성**: 유일성을 만족하는 속성의 수는 최소가 되어야 합니다.
3.  **불변성**: 주식별자가 지정되면 그 값은 변하지 않아야 합니다.
4.  **존재성 (NOT NULL)**: 반드시 데이터 값이 존재해야 합니다. (NULL 허용 안 됨)

#### 식별자 관계와 비식별자 관계
*   **식별자 관계 (실선)**: 자식 엔터티가 부모 엔터티의 주식별자를 상속받아 **자신의 주식별자(PK)**로 사용하는 강한 연결 관계입니다. (단점: PK 속성 수가 계속 증가하여 조인이 복잡해질 수 있음)
*   **비식별자 관계 (점선)**: 자식 엔터티가 부모의 주식별자를 받아 **일반 속성(FK)**으로 사용하는 약한 종속 관계입니다. (단점: 부모 데이터를 찾기 위해 불필요한 조인이 길게 발생하여 성능 저하 우려)
