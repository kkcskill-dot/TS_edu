# 3장. 인덱스 튜닝

인덱스 튜닝의 두 축: **① 테이블 랜덤 액세스 최소화**, **② 인덱스 스캔 효율화**.

## 3.1 테이블 액세스 최소화

### 인덱스 클러스터링 팩터 (CF)
**인덱스 키 순서와 테이블의 물리적 정렬이 얼마나 일치하는가.**
- CF 좋음(낮음): 같은 인덱스 범위가 **적은 수의 테이블 블록**에 모여 있음 → 랜덤 액세스 적음.
- CF 나쁨(높음): 흩어져 있어 행마다 다른 블록 → 랜덤 액세스 폭증.
> 같은 인덱스라도 CF에 따라 비용이 수십 배 차이. (실습: **클러스터링 팩터 시각화** 🆕)

### 인덱스 손익분기점
조회 건수가 늘수록 인덱스(랜덤 액세스)가 풀스캔(시퀀셜)보다 **불리해지는 지점**.
- 보통 전체의 **수~십수 %** 를 넘으면 풀스캔이 빠르다. CF가 나쁘면 손익분기점이 더 낮아진다.

### 인덱스만 읽고 처리 (커버링 인덱스)
필요한 컬럼이 **모두 인덱스에 있으면** 테이블 액세스를 생략한다.
```sql
-- (deptno, sal) 인덱스면 테이블 안 감
SELECT deptno, SUM(sal) FROM emp WHERE deptno = 10 GROUP BY deptno;
```
- **인덱스 컬럼 추가**로 커버링을 만들면 랜덤 액세스 제거.
- **IOT(인덱스 구조 테이블)**, **클러스터 테이블**도 랜덤 액세스 감소 기법.

## 3.2 부분범위 처리
결과 전체가 아니라 **클라이언트가 요청하는 만큼만(예: 첫 화면 10건)** 만들어 보내고 멈추는 방식.
- 인덱스로 정렬을 대체하면 **소트 없이** 앞부분만 빠르게 반환(OLTP 페이지 첫 화면 체감 성능↑).

## 3.3 인덱스 스캔 효율화

### 액세스 조건 vs 필터 조건
- **액세스 조건**: 인덱스 스캔 **시작/종료 지점**을 결정(스캔량을 줄임).
- **필터 조건**: 스캔하면서 **버리는** 조건(스캔량은 안 줄어듦).
> 같은 조건도 인덱스 컬럼 순서에 따라 액세스가 되기도, 필터가 되기도 한다.

### 선두 컬럼이 비등치(=)면 비효율
```sql
-- 인덱스 (dt, cd). dt 가 범위(between)면 cd 는 '필터'로 전락
WHERE dt BETWEEN :a AND :b AND cd = 'X'
```
→ 등치 조건 컬럼을 **선두**로 두는 게 군집성에 유리.

### 대표 기법
- **BETWEEN → IN-List**: 이산 값이면 IN으로 바꿔 각 값에 Range Scan.
- **IN은 '='의 OR**: IN-List는 여러 등치로 동작.
- **LIKE vs BETWEEN**: 스캔 범위 비교해 선택.
- 옵션 조건(`(:p IS NULL OR col = :p)`) 처리 방식별 장단점 비교.
- **함수기반 인덱스(FBI)** 로 함수 호출 부하 해소.

## 3.4 인덱스 설계
- **두 가지 핵심 기준**: ① 조건절에 **자주·등치로** 쓰는 컬럼을 선두에 ② 결합 인덱스 **선택도**.
- 소트 생략을 위한 컬럼 추가, **중복 인덱스 제거**, 인덱스 설계도 작성.
> 인덱스는 많을수록 좋은 게 아니다 — DML 부하·중복을 함께 본다. (연계: 고성능 DB 설계 인덱스 설계 🔗)

> ✅ **3장 핵심**: 랜덤 액세스(테이블)를 줄이고(커버링·CF), 인덱스 스캔량(액세스 조건)을 줄인다. 손익분기점을 넘으면 풀스캔이 답.
