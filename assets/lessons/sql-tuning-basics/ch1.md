# 1장. SQL 처리 과정과 I/O

SQL이 어떻게 해석·최적화되어 실행되는지, 그리고 성능을 좌우하는 **I/O**의 원리를 이해한다. 튜닝의 모든 출발점이다.

## 1.1 SQL 파싱과 최적화

### 선언적 질의 언어
SQL은 **무엇(What)** 을 원하는지만 적고, **어떻게(How)** 가져올지는 옵티마이저가 결정하는 **선언적·집합적** 언어다. 그래서 같은 결과라도 옵티마이저의 선택에 따라 성능이 천차만별이다.

### SQL 처리 과정
```
SQL 작성 → ① 파싱(Parsing) → ② 최적화(Optimization) → ③ 로우 소스 생성 → ④ 실행
```
- **파싱**: 문법·의미 검사, 라이브러리 캐시에서 동일 SQL 검색(공유 가능?)
- **최적화**: 옵티마이저가 여러 실행계획 후보 중 **최저 비용** 선택
- **실행계획**: 선택된 처리 절차(접근 경로·조인 방법·순서)

### SQL 옵티마이저
오라클은 **비용 기반 옵티마이저(CBO)** 를 사용한다. 통계정보(행 수, 분포, 인덱스 등)를 바탕으로 각 계획의 **예상 비용**을 계산해 가장 싼 것을 고른다.
> 통계가 부정확하면 비용 계산이 틀어져 **나쁜 계획**을 고른다 → 7장에서 상세.

### 실행계획과 비용
```sql
EXPLAIN PLAN FOR SELECT * FROM emp WHERE deptno = 10;
SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
```
```
| Id | Operation                   | Name    | Rows | Cost |
|  0 | SELECT STATEMENT            |         |   10 |    2 |
|  1 |  TABLE ACCESS BY INDEX ROWID| EMP     |   10 |    2 |
|* 2 |   INDEX RANGE SCAN          | EMP_IDX |   10 |    1 |
```
- **읽는 순서**: 들여쓰기가 깊은(안쪽) 것부터, 같은 깊이는 위에서 아래로.
- **Rows** = 예상 행 수(카디널리티), **Cost** = 예상 비용. 실측과의 차이가 튜닝 단서.

### 옵티마이저 힌트
옵티마이저의 판단을 **개발자가 강제**하는 지시. 주석 `/*+ ... */` 형태.
```sql
SELECT /*+ INDEX(e emp_idx) */ * FROM emp e WHERE deptno = 10;   -- 인덱스 강제
SELECT /*+ FULL(e) */          * FROM emp e WHERE deptno = 10;   -- 풀스캔 강제
SELECT /*+ LEADING(d e) USE_HASH(e) */ ...                        -- 조인 순서·방식
```
| 분류 | 대표 힌트 |
|---|---|
| 접근 경로 | `INDEX`, `FULL`, `INDEX_FFS` |
| 조인 방식 | `USE_NL`, `USE_HASH`, `USE_MERGE` |
| 조인 순서 | `LEADING`, `ORDERED` |
| 병렬 | `PARALLEL` |

> ⚠️ **힌트는 최후 수단**: 통계·SQL을 먼저 고친다. 힌트는 데이터 변화에 취약하고, 문법/위치가 틀리면 **조용히 무시**된다. (실습: 「힌트 실습」)

## 1.2 SQL 공유 및 재사용

### 소프트 파싱 vs 하드 파싱
파싱 시 라이브러리 캐시에서 **같은 SQL**을 찾으면:
- **소프트 파싱**: 캐시 적중 → 기존 계획 재사용(가벼움)
- **하드 파싱**: 캐시 미스 → 최적화 전 과정 수행(무거움, CPU·래치 경합)

### 바인드 변수의 중요성
값을 SQL에 직접 박으면(리터럴) 매번 **다른 SQL_ID** → 하드 파싱 폭증.
```sql
-- 리터럴: 매 실행 다른 SQL → 하드파스
SELECT * FROM emp WHERE empno = 7369;
SELECT * FROM emp WHERE empno = 7499;
-- 바인드: 텍스트 1개 → 1회 하드파스 후 공유
SELECT * FROM emp WHERE empno = :empno;
```
> OLTP에서 바인드 변수는 **선택이 아니라 필수**. (실습: 「바인드 변수 & 파싱」)

## 1.3 데이터 저장 구조 및 I/O 메커니즘

### SQL이 느린 이유
대부분 **느린 이유 = 과도한 I/O**(특히 디스크 랜덤 I/O)와 **불필요한 블록 액세스**다.

### 저장 구조 & 블록 단위 I/O
```
데이터베이스 → 테이블스페이스 → 세그먼트(테이블/인덱스) → 익스텐트 → 블록
```
오라클은 **블록(기본 8KB) 단위**로 I/O 한다. 1건만 필요해도 그 행이 든 블록 전체를 읽는다.

### 시퀀셜 vs 랜덤 액세스
- **시퀀셜 액세스**: 논리적으로 이어진 블록을 차례로(예: 인덱스 리프 스캔, 풀스캔)
- **랜덤 액세스**: 흩어진 블록을 한 건씩(예: 인덱스 → 테이블 ROWID 액세스). **튜닝의 핵심은 랜덤 액세스 최소화**.

### 논리적 I/O vs 물리적 I/O
- **논리적 I/O**: 버퍼 캐시에서 블록 읽기(`query`/`current`). 적을수록 좋다 — **튜닝 1차 지표**.
- **물리적 I/O**: 캐시에 없어 디스크에서 읽기(`disk`). 느리다.

### Single Block vs Multiblock I/O
- **Single Block I/O**: 한 번에 1블록(인덱스 경유 랜덤 액세스). `db file sequential read`
- **Multiblock I/O**: 한 번에 여러 블록(풀스캔). `db file scattered read` — 대량엔 더 효율적.

### Table Full Scan vs Index Range Scan
| | Full Scan | Index Range Scan |
|---|---|---|
| 읽기 | Multiblock(시퀀셜) | Single Block(랜덤) + 인덱스 |
| 유리 | 많은 행을 읽을 때 | 소량을 골라 읽을 때 |
> 둘의 **손익분기점**이 인덱스 튜닝의 핵심(3장). "인덱스 = 항상 빠름"은 오해다.

### 캐시 탐색 메커니즘
자주 읽는 블록은 **버퍼 캐시**에 둬서 물리 I/O를 줄인다. 해시 체인으로 블록 존재를 탐색하며, 이때 **버퍼 래치** 경합이 생길 수 있다.

> ✅ **1장 핵심**: SQL은 파싱→최적화→실행되며, 성능은 **I/O량(특히 논리적 I/O·랜덤 액세스)** 이 좌우한다. 바인드 변수로 파싱 부하를, 인덱스/풀스캔 선택으로 I/O를 통제한다.
