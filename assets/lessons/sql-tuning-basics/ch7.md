# 7장. SQL 옵티마이저

옵티마이저가 **어떻게 비용을 계산하고 계획을 고르는지**, 그 한계와 개발자의 역할.

## 7.1 통계정보와 비용 계산 원리

### 선택도(Selectivity)와 카디널리티(Cardinality)
- **선택도**: 조건을 만족하는 행의 **비율**(0~1). 등치 조건 선택도 ≈ `1 / NDV`(고유값 수).
- **카디널리티** = 전체 행 수 × 선택도 = **예상 결과 건수**.
> 카디널리티 추정이 틀리면 접근경로·조인방식·순서가 모두 어긋난다 → 튜닝의 핵심 진단 포인트.

### 통계정보
- **테이블**: 행 수, 블록 수, 평균 행 길이.
- **컬럼**: NDV, NULL 수, 최소/최대, **히스토그램**(분포 편향 반영).
- **인덱스**: BLEVEL(높이), 리프 블록 수, **클러스터링 팩터**.
```sql
EXEC DBMS_STATS.GATHER_TABLE_STATS('SCOTT','EMP', METHOD_OPT=>'FOR ALL COLUMNS SIZE AUTO');
```

### 비용 계산 원리
비용 ≈ **예상 I/O(블록 수) + CPU**. 인덱스 비용은 `BLEVEL + 리프 스캔 + 테이블 랜덤 액세스(CF 반영)`로 추정.

## 7.2 옵티마이저에 대한 이해
- **종류/모드**: CBO(비용 기반). 모드 `ALL_ROWS`(전체 처리량) vs `FIRST_ROWS(n)`(첫 n건 빠르게).
- **영향을 미치는 요소**: 통계, 파라미터(`OPTIMIZER_*`), 힌트, 제약·인덱스 구조, 바인드 변수(피킹).
- **옵티마이저의 한계**:
  - 통계가 부정확/부족하면 오판(카디널리티 오류).
  - **바인드 피킹**: 첫 실행 값으로 계획이 굳어 편중 데이터에서 불리(→ 적응형 커서/통계 피드백).
  - 복잡한 조건 상관관계(컬럼 간)를 독립 가정 → 과소추정.
- **개발자의 역할**: 옵티마이저가 좋은 선택을 하도록 **정확한 통계·좋은 SQL·적절한 인덱스**를 제공. 힌트는 최후 수단.
- **튜닝 전문가 되는 법**: 실행계획을 읽고(예상 vs 실측), 원인을 **수리적으로** 설명하는 습관.

> ✅ **7장 핵심**: 옵티마이저는 **통계 기반 카디널리티**로 비용을 계산한다. 통계 정확화가 튜닝의 8할. 한계(피킹·상관관계)는 적응형 기능과 확장통계로 보완. (실습: 플랜 진단 기초 ♻️ · 적응형 최적화 ♻️)
