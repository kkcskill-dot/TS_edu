ASH / AWR

"과거 그 순간, 시간이 어디로 갔는가"를 추적한다.
ASH(미시)·AWR(거시) 수집 원리부터 Load Profile 임계값·실전 케이스까지.

왜 사후 분석인가
장애는 끝났고 V$는 과거를 모른다

"그때는 멈췄는데, DBA가 접속하니 이미 정상" — V$SESSION은 실시간만 보여줄 뿐 과거 대기 구도를 역추적하지 못한다.

그래서: 엔진이 성능 이력을 메모리(ASH) + 디스크(AWR)에 자동 기록한다.
전형적 증상
  • 오전 9시 특정 화면만 느렸다는 신고 — 지금은 정상
  • 어젯밤 배치 3시간 동안 부하 추이를 알고 싶다
  • 실시간 뷰로는 "그 시각의 세션 분포" 복원 불가

미시 수집
ASH — 1초마다 활성 세션 스냅

주기 · 대상

1초마다 활성 세션만(ON CPU/WAITING) 샘플. 유휴(SQL*Net message from client)는 제외.

오버헤드

활성만 보므로 부하 1% 미만. 초고속 샘플링.

순환 버퍼: 가득 차면 오래된 것부터 덮어씀 → 메모리엔 보통 최신 1~2시간만.
디스크 영속화(MMNL)
  • ASH 버퍼 60% 차거나 10초마다 동작
  • 버퍼의 10%만 압축 샘플링(10초당 1건 수준)
  • 대상: SYS.WRH$_ACTIVE_SESSION_HISTORY
  • 그래서 디스크 ASH는 메모리보다 성기다
거시 영속화
AWR — 1시간 스냅샷

MMON

1시간마다 누적 통계(CPU·블록 I/O·SQL 수행량) 스냅샷을 디스크에 영구 기입.

보존

기본 8일. 간격·보존기간은 설정으로 늘릴 수 있음.

실무 메모
  • 리포트: @?/rdbms/admin/awrrpt.sql(구간 스냅 선택)
  • 스냅 간격↓·보존↑은 SYSAUX 용량과 트레이드오프
  • 두 스냅 사이의 델타로 구간 부하를 계산
  • AWR/ASH는 Diagnostics Pack 라이선스 영역

SELECT LEVEL, ash.session_id, ash.blocking_session, ash.event, ash.sql_id FROM v$active_session_history ash WHERE ash.sample_time = TIMESTAMP '2026-05-18 14:32:12' START WITH ash.blocking_session IS NOT NULL CONNECT BY PRIOR ash.session_id = ash.blocking_session AND PRIOR ash.sample_time = ash.sample_time;
동작 원리
  • 같은 샘플 시각 안에서 트리 추적(시점 고정)
  • 루트 = 남을 막지만 자긴 안 막힌 최상단 세션
  • 그 세션을 KILL 등 의사결정
  • 1회차의 V$SESSION Wait-For Graph의 ASH 버전
Load Profile
DB Time 과 AAS 임계값
DB Time = CPU + Wait
AAS = DB Time / Snapshot 구간(초)
AAS 판단 기준
  • AAS < 코어수 — 여유, 안전
  • AAS ≈ 코어수 — 100% 풀가동, 초임계
  • AAS > 코어수 — Run Queue 적체, 지수적 지연(위험)
Load Profile
Hard Parses/s — 파싱 폭주 감지
Hard Parses/s = Hard Parses / Elapsed(초)

정상

< 5.0 /s

위험

≥ 100 /s → Shared Pool 래치로 CPU 풀가동, Hang 근접

왜 위험한가
  • 새 SQL마다 최적화·플랜 생성(컴파일)
  • 공유 풀 힙에 노드 할당 → 래치 경합
  • 디스크 I/O 없이 CPU만 100%
  • 원인 99%는 바인드 변수 누락
Instance Efficiency
캐시·파싱 효율 백분율
Buffer Hit % = (1 − 물리/논리 읽기) × 100정상 ≥ 95% · 낮으면 디스크 직접 읽기(인덱스 부재 등)
Soft Parse % = (1 − 하드/전체 파싱) × 100정상 ≥ 99.9% · 99% 미만이면 리터럴 결합 의심
해석 포인트
  • Buffer Hit 낮음 → scattered/sequential read 상위 예상
  • Soft Parse 낮음 → latch: shared pool 동반
  • 두 지표는 증상 — Top SQL로 원인까지
  • Hit율이 높아도 비효율 SQL(과다 논리읽기) 가능
대기 이벤트 ①
db file sequential read

단일 블록 물리 읽기 — 인덱스 경유 시 캐시에 없어 한 블록씩 디스크에서.

진단

넓은 범위를 인덱스 Range Scan → 수십만 랜덤 I/O.

조치

넓으면 /*+ FULL */로 다중블록, 또는 결합 인덱스로 Index Only.

주의
  • 이미 인덱스를 쓰는데 1위 → 인덱스 추가가 답이 아님
  • 결합 인덱스 순서 최적화가 먼저
  • 넓은 범위면 차라리 FTS 유도
대기 이벤트 ②
db file scattered read

다중 블록 읽기 — FTS/Index FFS가 연속 블록을 캐시 여러 슬롯에 흩어 적재.

진단

인덱스 부재, 또는 조건절 변형(TO_CHAR(reg_date))으로 인덱스 무력화.

조치

WHERE 컬럼에 인덱스, 좌변 변형·LIKE '%abc' 제거 → Range Scan 복귀.

이름의 유래
  • 디스크에 뭉친 블록이 캐시의 불연속 슬롯으로 흩어짐(scattered)
  • 대량 추출엔 FTS가 오히려 유리
  • 묵시적 형변환이 흔한 무력화 원인(3회차 케이스)
대기 이벤트 ③
enq: TX - row lock contention

한 세션이 UPDATE/DELETE로 행에 배타락 → 같은 행 수정 세션이 무한 대기.

진단

Blocker가 INACTIVE/Client Idle로 락만 쥐고 있으면 Connection Leak.

조치

예외 시 rollback() 보장 + 풀 타이머(maxLifetime) 회수.

실무 체크리스트
  • try-catch에 rollback 누락 여부
  • finally에서 close 전 트랜잭션 종결
  • 풀: transactionTimeout, leak detection
  • 대기 회피: FOR UPDATE NOWAIT / SKIP LOCKED
대기 이벤트 ④
latch: shared pool / library cache

하드 파싱이 공유 풀 힙에 플랜을 적재하며 래치(상호배제)를 다툼.

진단

Hard Parses/s 급등 + I/O 없이 CPU 100%.

조치

리터럴 동적쿼리 제거 → 바인드 파라미터(플랜 재사용 99.9%).

임시 처방 · 주의
  • CURSOR_SHARING=FORCE로 리터럴 강제 치환(임시)
  • 근본은 앱의 바인드 변수 적용
  • FORCE는 히스토그램·플랜 품질 저하 부작용 가능
케이스 ① Connection Leak
예외 처리 결함 → 락 78%
// AS-IS — 예외 났는데 rollback이 없다 catch (Exception e) { System.err.println(e.getMessage()); // 🚨 락 방치 } finally { conn.close(); } // 미해제 채로 풀 반환 // TO-BE — 예외 시 즉시 롤백 보장 catch (Exception e) { if(conn!=null) conn.rollback(); throw ...; }
분석 단계
  • AWR: enq: TX가 DB Time 78%
  • ASH 14:32: 다수 세션이 BLOCKING=SID 412 지목
  • 412는 INACTIVE인데 락만 점유 → 누수 확정
케이스 ② Hard Parse
리터럴 남발 → CPU 100%

분석 수치
  • Hard Parses/s 1 → 385
  • Soft Parse % 32.4%로 폭락
  • CPU time 85% + latch: shared pool 10%
  • 개선 후 CPU 0%대 수렴
한 장 정리
2회차 핵심
  • ASH(1초·미시) ↔ AWR(1시간·거시)로 과거 복원
  • 핵심 컬럼 SESSION_STATE·EVENT·BLOCKING_SESSION
  • 임계값: AAS vs 코어 · Hard Parse<5 · Hit≥95% · Soft≥99.9%
  • 4대 이벤트 = I/O(seq/scattered) · 락(TX) · 파싱(latch)
  • 실전: Connection Leak · Hard Parse는 앱 코드가 원인
평가 포인트
  • AAS 8 / 코어 4 → 위험. 증설 전 SQL 튜닝 먼저
