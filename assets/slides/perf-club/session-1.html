사용자는 인스턴스(메모리)를 통해서만 디스크 데이터에 접근한다. 백그라운드 프로세스가 그 사이를 중계한다.

부가자료 · 기동 3단계
  • NOMOUNT — 파라미터파일 읽고 인스턴스(SGA·프로세스)만 기동
  • MOUNT — 컨트롤 파일을 열어 DB 구조 인식
  • OPEN — 데이터·리두 파일 열어 서비스 시작
  • 한 인스턴스 = 한 DB(단일). RAC는 여러 인스턴스가 한 DB 공유
  • 12c+ 멀티테넌트: CDB(컨테이너) 안에 PDB(플러그형 DB)
공유 메모리
SGA — System Global Area

Buffer Cache

데이터 블록 캐싱. 논리적 읽기의 대상.

Redo Log Buffer

변경 내용을 디스크 기록 전 임시 저장.

Shared Pool

파싱된 SQL·실행계획(라이브러리 캐시) 캐싱.

Lock / 기타

락 정보 등 공유 제어 구조.

심화 · 더 들여다보기
  • Shared Pool = Library Cache(SQL/커서) + Data Dictionary Cache(메타)
  • Large Pool: 병렬·RMAN·공유서버용 대형 할당
  • Buffer Cache는 LRU로 관리, 더티 블록은 DBWn이 기록
  • 크기: SGA_TARGET/MEMORY_TARGET로 자동 관리(ASMM/AMM)
  • 진단: V$SGASTAT, V$SGA_TARGET_ADVICE

트랜잭션의 두 기록
Redo("다시 하기") vs Undo("실행 취소")

REDO

장애 복구를 위해 모든 변경을 선기록(WAL). 커밋은 리두 기록을 보장.

UNDO

변경 전 데이터 보존 → ROLLBACK + 다중 사용자 읽기 일관성.

읽기 일관성: 내가 커밋 안 한 변경을 남이 못 본다 — 그 "과거 값"의 출처가 Undo.
심화 · 핵심 개념
  • WAL(Write-Ahead Logging): 데이터파일보다 리두를 먼저 쓴다
  • SCN(System Change Number): 변경의 논리적 시계 — 일관성 기준
  • Flashback Query(AS OF)는 Undo를 읽어 과거 조회
  • Commit ≠ 데이터파일 기록. 커밋은 리두만 보장(Fast Commit)
장애 시나리오 ①
Redo 100% → DB Hang
아카이빙 지연 / 폭증→ 덮어쓸 리두 공간 없음→ Log Switch Hang

리두 로그는 그룹을 순환(Circular)하며 덮어쓴다. 여분이 없으면 로그 스위치가 멈춘다.

현상: 시스템 전체 DML 멈춤(Hang). 사용자는 무한 대기(Lock Waiting).
진단 · 조치
  • 진단: V$LOG(상태 ACTIVE/CURRENT), V$LOG_HISTORY(스위치 빈도)
  • 대기: log file switch (archiving needed)
  • 조치: 아카이브 목적지 공간 확보가 1순위
  • 구조 개선: 리두 그룹·멤버 크기/개수↑, ARCn 병렬
  • 예방: 대량 적재 전 아카이브 모니터링
장애 시나리오 ②
Undo 100% → DML 실패 & 조회 에러
DML 불가: 변경 전 값 기록할 Undo 공간 부족 → INSERT/UPDATE/DELETE 실패
ORA-30036: unable to extend segment ... in undo tablespace
조회 실패: 장시간 SELECT가 참조할 과거 Undo가 덮어써져 유실
ORA-01555: snapshot too old
조치 · 예방
  • UNDO_RETENTION(초) — 과거 이미지 보존 시간
  • Undo TS 자동확장 + 충분한 크기
  • 장기 배치 SELECT와 고빈도 갱신 시간 분리
  • 건별 커밋 자제 — 너무 잦은 커밋도 ORA-01555 유발
  • 진단: V$UNDOSTAT, DBA_UNDO_EXTENTS
실시간 관측의 창
V$SESSION 파헤치기

디스크 테이블이 아니라 SGA 메모리 구조체(C 배열)를 SQL로 매핑한 동적 성능 뷰.

SELECT sid, serial#, username, status, machine, program, sql_id, sql_exec_start, prev_sql_id FROM v$session WHERE status='ACTIVE' AND sql_id IS NOT NULL;
관련 뷰 지도
  • V$PROCESS — OS 프로세스 ↔ 세션 매핑
  • V$SQL / V$SQLAREA — SQL 통계(buffer_gets 등)
  • V$SESSION_WAIT — 현재 대기 상세
  • V$ACTIVE_SESSION_HISTORY — 과거 샘플(2회차)
  • GV$ = RAC 전역(모든 노드), V$ = 내 노드만
컬럼 해독
세션을 읽는 4개의 렌즈
분류컬럼
식별SID, SERIAL#, USERNAME, SCHEMANAME
상태STATUS(ACTIVE/INACTIVE/KILLED), TYPE
클라이언트OSUSER, MACHINE, PROGRAM, MODULE
시간/SQLLOGON_TIME, SQL_ID, PREV_SQL_ID
실무 팁 · 범인 추적
  • MODULE/ACTION은 앱이 태깅(DBMS_APPLICATION_INFO) → 어느 화면/배치인지
  • CLIENT_IDENTIFIER로 커넥션 풀 뒤의 실사용자 추적
  • LAST_CALL_ET — 현재 상태 지속 시간(유휴 점유 탐지)
  • 백그라운드는 USERNAME이 NULL — TYPE='USER'로 필터
부하 지표
AAS — 평균 활성 세션
AAS = DB Time / Elapsed Time예) 60초 동안 DB Time 240초 → 240 / 60 = 4

그 60초 동안 평균 4개 세션이 1초도 쉬지 않고 부하를 줬다는 뜻 — 부하의 강도를 한 숫자로.

관련 개념
  • DB Time = CPU Time + Wait Time(non-idle)
  • AAS 1.0 ≈ "CPU 코어 1개를 꽉 채운 만큼"의 부하
  • 출처: V$SYS_TIME_MODEL, ASH 샘플 집계
  • AWR 리포트 상단 "Average Active Sessions"가 바로 이 값
Queueing 관점
AAS vs CPU 코어수(N)

AAS < N — 정상

Run Queue 대기 없음. 즉시 CPU 할당.

AAS ≫ N — 지연

잦은 컨텍스트 스위칭. 연산보다 스레드 교체 오버헤드 급증.

1차 판단: "부하가 서버의 물리적 동시처리 한계(N)를 넘었는가?"
참고 · OS 관점
  • OS의 Run Queue 길이(load average)와 직결
  • vmstat의 r 컬럼 = 실행 대기 프로세스 수
  • 임계점 AAS ≈ N 부근부터 응답시간 급격히 악화(M/M/c 큐잉)
  • CPU 대기는 ASH의 ON CPU 비중으로 확인
Root Cause 집계
이벤트별 Active 세션 그룹화
SELECT event, state, COUNT(*) cnt FROM v$session WHERE status='ACTIVE' AND type='USER' GROUP BY event, state ORDER BY cnt DESC;
해석법
  • 상위 EVENT = 병목의 성격(I/O? 락? 파싱?)
  • STATE: WAITING(대기 중) vs ON CPU(연산 중)
  • EVENT가 SQL*Net message from client면 유휴 — 제외
  • 다음 단계: 상위 이벤트를 6대 분류로 매핑 →
대기 이벤트 ①
db file sequential read

단일 블록 I/O — 한 블록을 버퍼 캐시로 올릴 때의 동기 대기.

원인

주로 인덱스 Range Scan. 선택도 낮아 과도한 랜덤 I/O.

해결

추출량 10~15% 초과면 Full Scan(순차)이 유리. 조건 변별력↑.

수치 · 판단 기준
  • 손익분기 ~10–15%(클러스터링 팩터에 따라 변동)
  • 랜덤 I/O 1건 ≈ 수 ms — 누적되면 치명
  • V$SQL의 BUFFER_GETS vs DISK_READS 비교
  • 클러스터링 팩터 나쁘면 적은 행도 많은 블록 접근
  • 대상: S.EVENT='db file sequential read' ⋈ V$SQL
대기 이벤트 ②
db file scattered read

다중 블록 I/O — 연속 블록을 한 번에 읽어 캐시에 흩어 적재.

원인

인덱스 부재 또는 옵티마이저의 FTS 선택(Full Table Scan).

해결

대용량 무조건 FTS는 I/O 고갈. 악성 세션 식별 + 필수 조건 강제.

판단 · 균형감
  • FTS가 항상 나쁜 건 아님 — 대량 추출엔 오히려 유리
  • 한 번에 읽는 블록 수: db_file_multiblock_read_count
  • 파티션 프루닝으로 스캔 범위 축소
  • 병렬 쿼리로 대용량 FTS 분산
  • 진행률: V$SESSION_LONGOPS(Table Scan)
대기 이벤트 ③
direct path read / temp

SGA 공용 캐시를 건너뛰고 PGA로 직접 I/O. 그리고 TEMP 스왑.

원인

대규모 정렬·해시가 PGA 초과 → TEMP를 스왑처럼(Out-of-Core).

해결

배치 단위 분할, PGA_AGGREGATE_TARGET 검토.

관련 파라미터 · 뷰
  • PGA_AGGREGATE_TARGET / _LIMIT
  • V$SQL_WORKAREA — Optimal/OnePass/MultiPass
  • TEMP 사용: V$SORT_USAGE(세션별 MB)
  • TEMP 부족 시 ORA-01652: unable to extend temp
  • 해시 조인 메모리 > 소트 — 큰 작업은 분할
대기 이벤트 ④
log file sync

WAL 동기화 지연 — COMMIT마다 리두 버퍼를 디스크에 기록 완료까지 대기.

원인

스토리지 쓰기(IOPS) 저하, 또는 반복문 건별 COMMIT.

해결

JDBC Batch로 묶어 단일 트랜잭션 — I/O 콜 최소화.

관련 · 깊게
  • 짝꿍 이벤트 log file parallel write(LGWR의 실제 쓰기) 비교
  • 리두 로그를 빠른/분리된 디스크에 배치
  • 커밋 폭주 세션: user commits(V$SESSTAT) Top-N
  • 비동기 옵션 COMMIT_WAIT=NOWAIT(정합성 트레이드오프, 신중)
대기 이벤트 ⑤
library cache lock / pin

공유 풀의 파싱된 SQL·객체 구조(AST)를 보호하는 상호 배제(Mutex) 락.

원인

운영 중 DDL(ALTER)·프로시저 재컴파일 → 참조 세션 전부 차단.

해결

유발 세션 식별·종료. 스키마 변경은 점검 시간에만.

관련 · 파싱 경합
  • 유사: cursor: pin S wait on X(커서 뮤텍스 경합)
  • DDL은 객체 커서를 무효화(invalidation) → 재파싱 폭발
  • 하드 파싱 과다 → 바인드 변수로 커서 공유
  • 운영 중 GRANT/통계수집도 무효화 유발 가능
대기 이벤트 ⑥
enq: TX - row lock contention

같은 레코드에 다수 세션이 동시 쓰기 → 무결성 보호 락.

원인

갱신 집중, 또는 예외 누락으로 락 점유 방치(Connection Leak).

해결

락 트리 순회로 Root Blocker 식별.

-- Wait-For Graph (LEVEL 1 = 임계구역 점유) START WITH blocking_session IS NULL CONNECT BY PRIOR sid = blocking_session
관련 · 락 진단
  • V$LOCK, V$SESSION.BLOCKING_SESSION
  • TX 락 외 ITL 부족(enq: TX - allocate ITL)도 행 락처럼 보임
  • 데드락 → ORA-00060(자동 희생자 롤백 + trace)
  • 대기 회피: SELECT ... FOR UPDATE NOWAIT / SKIP LOCKED
함부로 손대지 마라
장애 조치 3대 제약

① 무작정 Kill 금지

DML 세션 Kill → Undo 롤백. 대량이면 롤백이 더 오래, 그동안 락 유지.

② 부하 중 딕셔너리 조인 금지

DBA_OBJECTS 등 복잡 조인은 붕괴 유발. 가벼운 V$만.

③ Connection Storm 방지

재요청 폭주 → 풀 고갈. 서킷 브레이커·재시도 제한.

추가 원칙
  • 조치 전 스냅샷(현재 세션·SQL·락 상태 보존)
  • ALTER SYSTEM KILL SESSION vs DISCONNECT ... IMMEDIATE
  • 롤백 진행률: V$TRANSACTION.USED_UREC 감소 추세 확인
  • 단계적 조치 — 가장 상위 Root Blocker 하나부터
