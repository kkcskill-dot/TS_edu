제 1과목. 데이터 모델링의 이해

건물을 짓기 전 설계도가 필요하듯, DB를 구축하기 전 모델링이 필요합니다.

1과목 · 데이터 모델링
데이터 모델링의 3단계
단계특징설명
1. 개념적 모델링추상화 수준 최고
업무 중심적		전사적 아키텍처(EA) 수립.
핵심 엔터티와 관계 도출.
2. 논리적 모델링재사용성 최고
정규화 수행		데이터 모델링의 꽃.
테이블, 식별자, 관계 정의.
3. 물리적 모델링구체화 수준 최고
성능 고려		실제 DB에 이식 (오라클 등).
파티셔닝, 인덱스 등 설계.
강의 포인트
  • 시험 출제 1순위! 3단계의 순서와 특징을 명확히 비교해 줍니다.
  • 개념적 -> 논리적 -> 물리적으로 갈수록 구체화됨을 강조.
  • 특정 DBMS 종속은 오직 물리적 모델링뿐입니다.
1과목 · 데이터 모델링
데이터 독립성 (3단계 스키마)

외부 스키마

사용자, 응용 프로그래머가 접근하는 각각의 뷰(View)

개념 스키마

조직 전체의 통합된 데이터 구조 (DB 설계의 중심)

내부 스키마

물리적 저장 장치에 데이터가 저장되는 방법

독립성의 핵심
  • 논리적 독립성: 개념 스키마 변경 ➔ 외부 스키마 영향 無
  • 물리적 독립성: 내부 스키마 변경 ➔ 개념 스키마 영향 無
  • "DB 서버 디스크를 바꿔도, 사용자는 똑같이 쓴다" (물리적 독립성)
1과목 · 데이터 모델링
엔터티 (Entity)의 특징
  • 1. 업무에서 필요로 하는 정보여야 함
  • 2. 유일한 식별자로 구별 가능해야 함
  • 3. 2개 이상의 인스턴스의 집합
  • 4. 반드시 속성(Attribute)을 가짐
  • 5. 업무 프로세스에 의해 이용되어야 함
  • 6. 최소 1개 이상의 관계를 가짐
오답 노트
  • "고립된 엔터티는 좋은 설계다?" ➔ NO (관계 필수)
  • "속성이 없는 엔터티도 있다?" ➔ NO (속성 필수)
  • 공통코드, 통계성 엔터티는 예외적으로 관계 생략 가능.
1과목 · 데이터 모델링
발생 시점에 따른 엔터티 분류
분류특징예시
기본 (Fundamental)독립적 생성, 부모 없음사원, 부서, 고객, 상품
중심 (Main)기본 엔터티에서 파생, 업무의 중심계약, 주문, 청구, 매출
행위 (Active)2개 이상 부모에서 파생, 데이터 수시 변경주문이력, 접속로그
이해하기
  • 기본 ➔ 중심 ➔ 행위 순으로 도출됩니다.
  • 로그(Log)나 이력(History) 테이블은 대부분 행위 엔터티입니다.
1과목 · 데이터 모델링
속성 (Attribute)

기본 속성

업무에서 처음부터 도출됨.
(이름, 가입일)

설계 속성

시스템 설계를 위해 새로 만듦.
(고객번호, 지점코드)

파생 속성

다른 속성에서 계산/파생됨.
(총주문금액, 평균점수)

원자성의 원칙
  • 속성은 반드시 하나의 값(원자값)만 가져야 합니다.
  • 하나의 속성에 여러 값이 들어가면 1차 정규화 대상입니다.
  • 파생 속성은 데이터 정합성 유지를 위해 가급적 적게 정의.
1과목 · 데이터 모델링
식별자 (Identifier)의 4대 특징
  • 유일성 : 인스턴스를 유일하게 구별 (사번, 주민번호)
  • 최소성 : 유일성을 보장하는 최소한의 속성 조합
  • 불변성 : 한 번 지정되면 값이 변하지 않아야 함
  • 존재성 : NOT NULL (반드시 데이터가 있어야 함)
식별자 vs 비식별자 관계
  • 식별자 관계(실선): 부모 FK를 자식의 PK로 씀. (강한 종속)
  • 비식별자 관계(점선): 부모 FK를 자식의 일반 속성으로 씀. (약한 종속)
  • 실무에선 유연성을 위해 비식별자 관계를 많이 씁니다.

제 2과목. SQL 기본 및 활용

정규화와 성능 데이터 모델링

잘못된 설계가 부르는 재앙을 막는 '정규화'의 3단계를 시각적으로 파헤칩니다.

2과목 · 성능 모델링
제1정규형 (1NF) : 원자성 확보

[문제 테이블: 취미가 2개]

회원ID (PK)이름취미
U001김철수독서, 등산

[1차 정규화 완료: 1:M 분리]

회원ID (FK)취미
U001독서
U001등산
원자성 위배
  • 하나의 컬럼에 콤마(,)로 여러 값이 들어가면 절대 안 됩니다.
  • 이 경우, 자식 테이블을 새로 만들어 1:M 관계로 풀어냅니다.
2과목 · 성능 모델링
제2정규형 (2NF) : 부분 함수 종속성 제거

[문제 테이블: 복합키의 일부에만 종속]

주문번호(PK)상품코드(PK)수량상품명
O001P012노트북
O001P021마우스
O002P015노트북
부분 종속의 위험성
  • PK가 [주문번호+상품코드]입니다.
  • 그런데 `상품명`은 `주문번호`와 무관하게 `상품코드` 하나에만 종속됩니다!
  • 노트북 이름이 바뀌면 두 군데를 수정해야 하는 이상현상 발생.
  • 상품 테이블을 분리하여 해결합니다.
2과목 · 성능 모델링
제3정규형 (3NF) : 이행적 함수 종속 제거

[문제 테이블: 일반 속성끼리 종속]

사번(PK)이름부서코드부서명
1001김철수D01개발팀
1002이영희D01개발팀
이행적 종속
  • 사번 ➔ 부서코드 ➔ 부서명
  • 즉, `부서명`은 PK가 아닌 일반속성 `부서코드`에 종속되어 있습니다.
  • 부서 테이블을 별도로 떼어내어 조인(JOIN) 구조로 바꿉니다.
2과목 · 성능 모델링
반정규화 (De-normalization)
반정규화란? 시스템 성능 향상을 위해 의도적으로 정규화 원칙을 위배하고, 데이터 중복을 허용하는 기법.
  • 컬럼 중복: 조인(Join) 횟수를 줄이기 위해 부모 컬럼을 자식에 복사.
  • 파생 컬럼 추가: SUM, AVG 등 계산된 결과를 미리 테이블에 저장.
  • 테이블 병합/분할: 수직 분할, 수평 분할(파티셔닝).
Trade-off
  • 반정규화는 조회(SELECT) 속도를 올리지만, 데이터 무결성을 훼손할 위험이 큽니다.
  • 수정/삭제 시 중복 데이터를 모두 찾아 바꿔야 하므로 DML 성능은 오히려 떨어집니다.

제 2과목. SQL 기본 및 활용

SQL 기본 (SELECT와 함수)

개발자가 매일 쓰는 SQL. 그 안에 숨겨진 치명적인 함정들을 피하는 법.

2과목 · SQL 기본
SELECT 구문의 논리적 실행 순서 🏆
  1. FROM (테이블을 읽는다)
  2. WHERE (조건에 맞는 행 필터링)
  3. GROUP BY (그룹화)
  4. HAVING (그룹화된 결과 필터링)
  5. SELECT (출력할 컬럼 추출)
  6. ORDER BY (정렬)
실무·시험 최다 출제
  • "SELECT 절에서 만든 별칭(Alias)을 WHERE 절에서 쓸 수 없는 이유?"
  • ➔ 실행 순서상 WHERE가 SELECT보다 먼저 실행되기 때문!
  • 단, ORDER BY는 가장 마지막이므로 별칭 사용 가능.
2과목 · SQL 기본
NULL 데이터의 끔찍한 진실 🏆
NULL은 '0'이나 '빈칸'이 아닙니다. 아직 모르는 미지의 값(Unknown)입니다!
  • 사칙 연산: 100 + NULL = NULL. 연산 결과는 무조건 NULL!
  • 비교 연산: NULL = NULL 은 UNKNOWN(거짓). IS NULL을 써야 함.
  • 집계 함수: SUM, AVG는 NULL이 포함된 행을 무시(제외)하고 계산합니다.
집계 함수 함정
  • A(100), B(200), C(NULL) 일 때,
  • AVG(점수)의 분모는 3명이 아니라 2명이 됩니다! (150 반환)
  • 이걸 막으려면 AVG(NVL(점수, 0))를 써야 합니다.
2과목 · SQL 기본
WHERE vs HAVING
SELECT 부서, SUM(급여) FROM 사원 WHERE 직급 = '과장' -- 1. 과장만 추림 (행 필터링) GROUP BY 부서 -- 2. 부서별로 묶음 HAVING SUM(급여) > 5000; -- 3. 총합이 5천 넘는 부서만 (그룹 필터링)
결정적 차이
  • WHERE: GROUP BY로 묶기 전에 개별 행을 필터링. (인덱스 사용 가능)
  • HAVING: GROUP BY로 묶은 후에 집계 함수 결과값으로 필터링.
  • HAVING 절에는 가급적 집계함수(SUM, COUNT 등) 조건만 넣는 것이 권장됩니다.

제 2과목. SQL 기본 및 활용

SQL 활용 (고급 기법)

조인(JOIN), 서브쿼리, 집합 연산자, 윈도우 함수 등 SQL 실력을 판가름하는 핵심 구역.

2과목 · SQL 활용
조인 (JOIN)의 집합적 이해

INNER JOIN

양쪽 테이블에 공통으로 매칭되는 데이터만 (교집합).

LEFT OUTER JOIN

왼쪽 테이블 데이터는 무조건 살리고, 오른쪽은 없으면 NULL로 채움.

FULL OUTER JOIN

매칭 안 되는 양쪽 데이터 모두 살림 (합집합).

CROSS JOIN

조건 없이 M × N 카티션 곱 생성. (12행)

강의 팁
  • 초보자들은 OUTER JOIN을 두려워합니다.
  • "고객이 한 번도 주문하지 않았더라도, 전체 고객 명단을 봐야 할 때" LEFT OUTER JOIN을 쓴다고 예시를 들어주세요.
2과목 · SQL 활용
서브쿼리 (Subquery) 위치별 명칭
위치명칭특징
SELECT 절스칼라 서브쿼리반드시 단일 행, 단일 컬럼만 반환해야 함. 결과가 2개 이상이면 에러.
FROM 절인라인 뷰실행 시점에 동적으로 생성되는 가상 테이블 역할.
WHERE 절중첩 서브쿼리IN, ANY, ALL, EXISTS 등과 함께 다중 행 비교에 주로 사용.
주의사항
  • 메인 쿼리는 서브쿼리의 컬럼을 쓸 수 없습니다! (단, 인라인 뷰 제외)
  • 서브쿼리는 괄호 `()` 로 감싸야 합니다.
2과목 · SQL 활용
집합 연산자
연산자의미정렬 작업 여부
UNION합집합 (중복 1개로 제거)O (느림)
UNION ALL합집합 (중복 모두 출력)X (매우 빠름)
INTERSECT교집합O
MINUS차집합 (A에서 B 뺌)O
핵심 포인트
  • UNION ALL을 제외한 연산자들은 내부적으로 중복 제거를 위해 정렬(SORT) 작업을 동반합니다.
  • 개발 시 중복이 없거나 상관없다면 무조건 UNION ALL을 쓰는 것이 성능에 탁월합니다!
2과목 · SQL 활용
윈도우 순위 함수 비교 🏆

점수: 100, 90, 90, 80점 순서일 때

함수명출력 순위특징
RANK()1, 2, 2, 4동점자는 묶고, 다음 순위를 건너뜁니다.
DENSE_RANK()1, 2, 2, 3빽빽하게(Dense)! 순위를 건너뛰지 않습니다.
ROW_NUMBER()1, 2, 3, 4무조건 고유한 일련번호를 매깁니다.
무조건 출제
  • SQLD 윈도우 함수 문제의 80%는 이 3가지 순위 함수의 차이점을 묻습니다.
  • `OVER (PARTITION BY 부서 ORDER BY 급여 DESC)` 형태로 그룹별 순위를 구하는 구문 구조를 눈에 익혀두세요.

제 2과목. SQL 기본 및 활용

관리 구문 & 성능 최적화 원리

DDL과 DML의 차이, 그리고 옵티마이저가 쿼리를 실행하는 내부 알고리즘.

2과목 · 관리구문 & 튜닝
DELETE vs TRUNCATE vs DROP
명령어분류대상Auto CommitRollback
DELETEDML행 단위 데이터XO (가능)
TRUNCATEDDL데이터 전체OX (불가)
DROPDDL테이블 구조OX (불가)
실무 대참사 주의
  • TRUNCATE는 Undo 로그를 남기지 않아 압도적으로 빠르지만, 절대 복구할 수 없습니다.
  • 오라클에서 DDL은 실행 즉시 자동 커밋됩니다. 이전의 DML 작업들도 함께 커밋되어 버리니 주의!
2과목 · 관리구문 & 튜닝
옵티마이저 (Optimizer)란?
우리가 던진 SQL을 어떻게 실행할지 가장 빠르고 저렴한 실행 계획(Execution Plan)을 세워주는 DB 내부 엔진입니다. (자동차 내비게이션 역할)
  • 규칙 기반 (RBO): 옛날 방식. 인덱스가 있으면 무조건 타는 등 미리 정해진 15개 규칙 준수.
  • 비용 기반 (CBO): 현대 방식. 테이블의 통계 정보(건수, 분포도 등)를 분석하여 CPU와 I/O 비용(Cost)이 가장 낮은 길을 계산해 선택.
인덱스를 못 타는 쿼리
  • 좌변 가공: `WHERE SUBSTR(사번,1,2) = '10'`
  • 부정형: `WHERE 사번 != '1001'`
  • NULL 검색: `IS NULL` (인덱스는 보통 NULL을 저장 안 함)
  • 위 경우 비싼 인덱스를 놔두고 Full Table Scan을 합니다.
2과목 · 관리구문 & 튜닝
조인 수행 알고리즘 🏆

NL Join (중첩 루프)

이중 For문 방식.
선행 데이터 1건마다 후행 테이블의 인덱스를 찾아감.
소량 데이터 처리에 유리.

Sort Merge Join

두 테이블을 각각 정렬(Sort)한 뒤 병합.
인덱스 없어도 가능. 비동등 조인 가능.
대용량 시 정렬 부하 큼.

Hash Join

선행 테이블로 해시 맵을 메모리에 만듦.
대용량 데이터 조인에 압도적 속도.
오직 동등(=) 조인만 가능.

튜닝의 기본
  • NL 조인은 무조건 후행 테이블에 인덱스가 필수입니다. 없으면 매번 Full Scan ➔ DB 마비!
  • 데이터 웨어하우스(DW) 대용량 집계는 대부분 Hash Join이 주름잡습니다.
